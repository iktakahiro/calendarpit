このガイドでは、Calendarpit のリポジトリをクローンしてローカルサーバーを起動し、付属のサンプルアプリを接続する手順を説明します。

## 必要な環境

- Git
- [Bun](https://bun.sh/) `1.4.3`（`.bun-version` で指定されているバージョン）

Google アカウント、Google Cloud プロジェクト、外部のデータベースサーバー、`.env` ファイル、API 認証情報は不要です。

現在、Calendarpit は npm パッケージ、コンテナイメージ、リリースバイナリとしては公開されていません。リポジトリをローカルにクローンして直接実行します。

## Calendarpit とサンプルアプリを起動する

<Steps>

1. **リポジトリをクローンして依存パッケージをインストールする**

   [https://github.com/iktakahiro/calendarpit](https://github.com/iktakahiro/calendarpit) をクローンし、Bun でロックファイルに従って依存パッケージをインストールします。

   ```sh
   git clone https://github.com/iktakahiro/calendarpit.git
   cd calendarpit
   bun install --frozen-lockfile
   ```

2. **Calendarpit を起動する**

   リポジトリのルートディレクトリでローカルサーバーを起動します。

   ```sh
   bun run dev
   ```

   Calendarpit は `http://127.0.0.1:4173` で待ち受けます。Google Calendar API v3 のエンドポイント、ローカル OAuth のエンドポイント、管理 API、管理画面はすべてこのオリジンを共有します。`bun run dev` は常にポート 4173 を使用し、すでに使用されている場合は終了します。別のポートを使用する方法は[起動と設定](/calendarpit/ja/running/)を参照してください。

   デフォルトでは、データは `apps/calendarpit/.calendarpit/calendarpit.sqlite` の SQLite ファイルに保存され、初回起動時に組み込みの起動時フィクスチャが投入されます。使い捨てのインメモリセッションとして実行する場合は、代わりに `CALENDARPIT_DATABASE=:memory: bun run dev` を実行してください。再起動時のデータの扱いについては、[ストレージと再起動](/calendarpit/ja/storage/)を参照してください。

3. **ヘルスチェック用エンドポイントを確認する**

   別のターミナルを開き、サーバーが動作していることを確認します。

   ```sh
   curl http://127.0.0.1:4173/__calendarpit/health
   ```

   このエンドポイントは、サーバーの状態と現在のストレージモード（`sqlite` または `memory`）を返します。

   ```json
   {
     "name": "Calendarpit",
     "version": "0.1.0",
     "stage": "preview",
     "storage": "sqlite",
     "capabilities": {
       "calendar": true,
       "oauth": true,
       "watch": true,
       "fixtures": true
     }
   }
   ```

4. **管理画面を開く**

   ブラウザで `http://127.0.0.1:4173` を開きます。デフォルトの起動時フィクスチャには、2 人のテストユーザー（`alex` と `sam`）、3 つのカレンダー、`2026-10-19` のイベント「Weekly planning」、サンプルアプリが使用する OAuth クライアント `sample-app` が含まれています。

   Schedule ビューはデフォルトで `2026-10-19` を表示します。管理画面は 2 秒ごとにサーバーをポーリングするため、API 経由で行った変更は自動的に画面へ反映されます。

5. **サンプルアプリを起動する**

   2 つ目のターミナルで、付属のサンプルアプリを起動します。

   ```sh
   bun run sample:dev
   ```

   ブラウザで `http://127.0.0.1:4175` を開きます。このサンプルアプリは、公式の `@googleapis/calendar` パッケージと `google-auth-library` パッケージを `http://127.0.0.1:4173` に向けて使用しています。

   認証には、クライアント ID `sample-app`、クライアントシークレット `local-sample-secret`、リダイレクト URI `http://127.0.0.1:4175/callback` を使用します。これらのクライアント認証情報は、デフォルトのフィクスチャに含まれているローカルテスト用の公開値です。

6. **カレンダーの一連の動作を試す**

   `http://127.0.0.1:4175` のサンプルアプリで、次の操作を試せます。

   - **Connect calendar** をクリックして OAuth の認可コードフローを開始し、同意画面でテストユーザーを選択してアクセスを承認します。
   - **Create event** をクリックして `2026-10-19` にイベントを作成し、FreeBusy クエリが返す busy 区間に新しいイベントが含まれていることを確認します。
   - **Start watch** をクリックして watch チャネルを開始し、`http://127.0.0.1:4175/notifications` で `events.watch` の Webhook 通知を受け取れるようにします。チャネルの開始時には、まず `sync` 通知が送信されます。その後、作成したイベントを更新または削除すると通知が配信されます。
   - **Revoke connection** をクリックしてアクセス権を取り消してから再接続するか、`http://127.0.0.1:4173` の管理画面で **API history** や **Watch** を開き、記録されたリクエストや Webhook の配信を確認します。

</Steps>
