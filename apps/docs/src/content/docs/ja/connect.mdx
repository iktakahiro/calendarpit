## プロバイダーの切り替えを追加する

Calendarpit を起動しても、Google 宛ての通信が自動的にインターセプトされるわけではありません。ローカル開発や自動テストで Calendarpit を使うには、OAuth クライアントと Google Calendar SDK クライアントを初期化するコードで接続先を切り替えられるようにします。

`CALENDARPIT_URL` のような環境変数名はアプリ側で自由に決められます。Google SDK が `CALENDARPIT_URL` を自動で読み込むことはないため、アプリの初期化コードで環境変数を読み込み、ローカルの URL を SDK に渡してください。

認証情報はプロバイダーごとに分けて管理してください。

- Calendarpit のアクセストークンとリフレッシュトークンは、ローカルのプロバイダーでのみ使用します。
- 本番の Google クライアントシークレットとトークンは、Google 用の設定にのみ保持します。本物の Google 認証情報をフィクスチャに含めないでください。

## すべてのプロバイダーエンドポイントを上書きする

Calendar API の URL を変更するだけでは不十分です。OAuth のエンドポイントがデフォルトのままだと、ブラウザのリダイレクト、トークン交換、トークン更新が Google に送信されてしまいます。次の 5 つのエンドポイントをすべて上書きしてください。

| 用途                             | ローカルのエンドポイント                |
| -------------------------------- | --------------------------------------- |
| 認可画面                         | `http://127.0.0.1:4173/oauth/authorize` |
| 認可コードの交換とトークンの更新 | `http://127.0.0.1:4173/oauth/token`     |
| ユーザープロフィール             | `http://127.0.0.1:4173/userinfo`        |
| Calendar API のルート            | `http://127.0.0.1:4173/`                |
| トークンの取り消し               | `http://127.0.0.1:4173/oauth/revoke`    |

JavaScript の Calendar SDK（`@googleapis/calendar`）は、`rootUrl` の末尾に `/calendar/v3/...` を付与します。`rootUrl` に `/calendar/v3` を含めないでください。Python、Go、.NET では、`/calendar/v3/` を含むサービス URL 全体を指定します。Java では、ルート URL とサービスパスを別々に設定します。詳しくは[SDK の使用例](/ja/sdks/)を参照してください。

watch のコールバック先アドレスは通信の向きが逆になり、Calendarpit からアプリ側へ送信されます（例: `http://127.0.0.1:4175/notifications`）。デフォルトで許可されるコールバック先のホストはループバック（`127.0.0.1`、`localhost`、`[::1]`）のみです。それ以外のホストを使う場合は、`CALENDARPIT_WATCH_HOSTS` で指定してください。詳しくは[watch 通知](/ja/watch/)を参照してください。

## テスト用の OAuth クライアントを登録する

Calendarpit は、認可エンドポイントで `client_id` と `redirect_uri` を検証し、`/oauth/token` で `client_id`、`client_secret`、および認可コード交換時の `redirect_uri` を検証します。フィクスチャの `clients` 配列にアプリを登録してください。

```json
{
  "clients": [
    {
      "id": "my-app",
      "secret": "local-test-secret",
      "redirectUris": ["http://127.0.0.1:3000/auth/google/callback"]
    }
  ]
}
```

フィクスチャはワークスペース全体を置き換えるため、`clients` とあわせて `users`（および `calendars`）も含めてください。サンプルアプリも併用する場合は、`sample-app` のエントリも残します。

起動時フィクスチャが適用されるのは、新規データベースまたは `:memory:` セッションのみです。実行中または保存済みのワークスペースを変更するには、`POST /__calendarpit/fixtures` でフィクスチャを読み込むか、新しいデータベースで起動してください。なお、ワークスペースをリセットすると API で読み込んだフィクスチャではなく、起動時フィクスチャの状態に戻ります。リセット後もクライアント定義を維持するには、新規データベースまたは `:memory:` セッションの起動時フィクスチャ（`--config` または `CALENDARPIT_CONFIG`）として渡すか、リセット後に再度読み込んでください。詳しくは[フィクスチャ](/ja/fixtures/)を参照してください。

- `redirectUris` には、アプリのコールバック URL を正確に指定します。Calendarpit は `redirect_uri` を文字列の完全一致で照合します。ポートのワイルドカードや末尾スラッシュの正規化は行いません。
- `secret` は必須です。PKCE フローを含め、すべての `/oauth/token` リクエストでこの値を `client_secret`（または HTTP Basic 認証）として送信する必要があります。

組み込みのデフォルトフィクスチャには、ローカルテスト用の OAuth クライアントが 1 件登録されています。

- クライアント ID: `sample-app`
- クライアントシークレット: `local-sample-secret`（公開されているローカルテスト用の値）
- リダイレクト URI: `http://127.0.0.1:4175/callback`

認可コード、トークン更新、`/userinfo`、取り消しまでの一連のフローは、[ローカル OAuth](/ja/oauth/)を参照してください。

## JavaScript の OAuth クライアントと Calendar クライアント

`@googleapis/calendar` と `google-auth-library` を使う場合は、`OAuth2Client` に `endpoints` を、Calendar クライアントに `rootUrl` を設定します。

```ts
import { calendar } from '@googleapis/calendar';
import { OAuth2Client } from 'google-auth-library';

const origin = 'http://127.0.0.1:4173';
const auth = new OAuth2Client({
  clientId: 'sample-app',
  clientSecret: 'local-sample-secret',
  redirectUri: 'http://127.0.0.1:4175/callback',
  endpoints: {
    oauth2AuthBaseUrl: `${origin}/oauth/authorize`,
    oauth2TokenUrl: `${origin}/oauth/token`,
    oauth2RevokeUrl: `${origin}/oauth/revoke`,
  },
});
const api = calendar({ version: 'v3', auth, rootUrl: origin });
// After the callback: auth.setCredentials((await auth.getToken(code)).tokens)
const profile = await auth.request({ url: `${origin}/userinfo` });
const calendars = await api.calendarList.list();
const { data } = await api.freebusy.query({
  requestBody: {
    timeMin: '2026-10-19T00:00:00+09:00',
    timeMax: '2026-10-20T00:00:00+09:00',
    items: [{ id: 'primary' }],
  },
});
console.log(data.calendars?.primary?.busy);
```

この例の 3 つの呼び出しをすべて実行できるよう、必要なスコープを含めて認可してください。たとえば `auth.generateAuthUrl({ access_type: 'offline', scope: ['https://www.googleapis.com/auth/calendar', 'email', 'profile'] })` のように指定します。

- `calendar.events` や `calendar.freebusy` のような狭いスコープでは、`calendarList.list` を呼び出せません。`calendarList.list` には `calendar`、`calendar.readonly`、`calendar.calendarlist`、`calendar.calendarlist.readonly` のいずれかが必要です。
- `/userinfo` には、`openid`、`email`、`profile`、または `userinfo.*` のスコープが必要です。`email` はメールスコープがある場合のみ、`name` はプロフィールスコープがある場合のみ返されます。
- リフレッシュトークンは、`access_type=offline` を指定した場合のみ発行されます。

スコープの一覧は[ローカル OAuth](/ja/oauth/)を参照してください。

`auth.setCredentials` で認証情報を設定すると、`OAuth2Client` によるトークン更新リクエストもローカルの `oauth2TokenUrl` に送られます。一方、`getTokenInfo` や `verifyIdToken` などの `OAuth2Client` のヘルパーは、`tokenInfoUrl` と証明書 URL も上書きしない限り Google へ通信します（サンプルアプリではこれらも上書きしています）。Calendarpit には対応するエンドポイントがなく、ID トークンも発行しないため、ローカルプロバイダーに対してこれらのヘルパーは呼び出さないでください。Python や Go など他の言語については、[SDK の使用例](/ja/sdks/)を参照してください。

## 参考実装のサンプルアプリ

リポジトリには、`@googleapis/calendar` と `google-auth-library` を使ったサンプルアプリが含まれています。Calendarpit の配布パッケージには含まれておらず、独自のアプリを接続する場合は不要です。試す場合は、[開発ガイド](https://github.com/iktakahiro/calendarpit/blob/main/docs/development.md)に従ってソースコードをチェックアウトし、別々のターミナルで実行してください。

```sh
# Terminal 1: start the packaged server
calendarpit serve

# Terminal 2: from the prepared source checkout
bun run sample:dev
```

Calendarpit は `http://127.0.0.1:4173`、サンプルアプリは `http://127.0.0.1:4175` で起動します。サンプルアプリは単一の接続を扱うローカルデモであり、アプリ実装の参考になる次の 2 つの仕組みを含んでいます。

- **state Cookie の検証**: OAuth の `state` パラメータを有効期間 5 分の HttpOnly Cookie（`sample_state`）に保存し、認可コードを交換する前に `/callback` で検証します。
- **ループバック限定の送信ガード**: SDK が送信するリクエストのうち、宛先ホストが `127.0.0.1`、`localhost`、`[::1]` 以外のものをブロックし、HTTP リダイレクトも拒否します。これにより、誤って本物の Google サーバーへリクエストが送信されるのを防ぎます。

サンプルアプリは次の環境変数を使用します。

| 環境変数               | デフォルト                           |
| ---------------------- | ------------------------------------ |
| `CALENDARPIT_URL`      | `http://127.0.0.1:4173`              |
| `SAMPLE_PORT`          | `4175`                               |
| `SAMPLE_CLIENT_ID`     | `sample-app`                         |
| `SAMPLE_CLIENT_SECRET` | `local-sample-secret`                |
| `AUTHORIZATION_URL`    | `${CALENDARPIT_URL}/oauth/authorize` |
| `TOKEN_URL`            | `${CALENDARPIT_URL}/oauth/token`     |
| `USERINFO_URL`         | `${CALENDARPIT_URL}/userinfo`        |
| `CALENDAR_API_URL`     | `${CALENDARPIT_URL}`                 |

サンプルアプリは、取り消し URL を `${CALENDARPIT_URL}/oauth/revoke` に、リダイレクト URI を `http://127.0.0.1:<SAMPLE_PORT>/callback` に設定します。組み込みの `sample-app` クライアントに登録されているのはポート `4175` のみであるため、`SAMPLE_PORT` を変更する場合はフィクスチャの `redirectUris` もあわせて更新してください。

## 接続設定のチェックリスト

アプリで Calendarpit との連携を実装・運用する際は、次の点を確認してください。

- **全エンドポイントの上書き**: 認可、トークン交換、トークン更新、ユーザープロフィール、Calendar API の呼び出し、トークン取り消しが、すべてローカルのエンドポイントに向いていること。
- **コールバックの到達性**: ブラウザからアプリの OAuth `redirect_uri` にアクセスできること。また、Calendarpit からアプリの watch 用 Webhook アドレスに到達できること（Webhook のホストがループバック以外の場合は `CALENDARPIT_WATCH_HOSTS` を設定します）。
- **一連のフローの検証**: ログイン、イベントの読み書き、watch 通知、トークン更新、取り消し、ワークスペースのリセットを通じて、UI とバックグラウンドワーカーをテストすること。
- **アプリ固有のフィクスチャ管理**: アプリ固有のフィクスチャや E2E テストのシナリオは、アプリ側のリポジトリで管理すること。
