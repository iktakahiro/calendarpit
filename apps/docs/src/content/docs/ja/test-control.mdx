title: テスト制御 API
description: 自動テストの中で、HTTP を使って状態のリセット、フィクスチャの読み込み、リクエスト履歴の確認、Webhook 配信のドレインを行います。
---

Calendarpit には、`/__calendarpit` の下にローカルの管理 API があります。この API で、データの投入、サーバー状態の確認、テストの実行ごとのリセットができます。

## リクエストのルール

- **ベースパス:** 管理エンドポイントのパスは、すべて `/__calendarpit` で始まります（例: `http://127.0.0.1:4173/__calendarpit/reset`）。
- **認証なし:** 管理エンドポイントにベアラートークンは不要です。Calendarpit はローカル開発用のサーバーで、デフォルトではループバックアドレスにバインドします。コンテナ内などでループバック以外のアドレスにバインドした場合は、そのポートに接続できる人なら誰でもこれらのエンドポイントを呼び出せます。
- **書き込みには `Content-Type: application/json` が必要:** `GET` と `HEAD` 以外のリクエストでは、`application/json` で始まる `Content-Type` ヘッダーを送ってください（大文字と小文字は区別されます）。`DELETE` のルートや、ボディを受け取らない `POST` 制御も対象です。このヘッダーがない場合、リクエストは HTTP `415`（`unsupportedMediaType`）で失敗します。ボディを受け取らない `POST` 制御には、空のボディか `{}` を送ってください。
- **同一オリジンのチェック:** `Origin` ヘッダーがサーバーのオリジンと一致しない場合や、`Sec-Fetch-Site: cross-site` が付いている場合、リクエストは HTTP `403`（`forbidden`）で失敗します。`curl` やテストランナーのようなブラウザ以外のクライアントは、通常 `Origin` を送らないため許可されます。`/__calendarpit/health` はこれらのチェックの対象外です。そのため、`GET` や `HEAD` による起動確認に追加のヘッダーは要りません。
- **履歴に残らない:** `/__calendarpit/*` へのリクエストは、プロトコルのリクエスト履歴に記録されません。
- **エラー形式:** 管理 API のエラーは、Google の JSON エラー形式に `domain: "calendarpit"` を入れて返されます。

## 管理エンドポイント

次の表のパスは、すべて `/__calendarpit` からの相対パスです。

| メソッド                           | パス                               | 動作                                                                                                                                                                                                                                |
| ---------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET` / `HEAD`                     | `/health`                          | サーバーの `name`（`"Calendarpit"`）、`version`（例: `0.1.0`）、`stage`、`storage`（`"memory"` または `"sqlite"`）、機能フラグ（`calendar`、`oauth`、`watch`、`fixtures`）を返します。`HEAD` は空の `200` を返します。              |
| `GET`                              | `/state`                           | 期限切れのチャネルを削除してから、`storage`、`users`、`calendars`、`events`、`clients`（シークレットなし）、`connections`、`channels`（`token` は伏せ字）、`deliveries`、`notifications`、`revision` のスナップショットを返します。 |
| `POST`                             | `/fixtures`                        | ユーザー、カレンダー、イベント、クライアントを検証して置き換えます。ランタイム状態をクリアし、接続を無効にします（`200` でスナップショットを返します）。                                                                            |
| `POST`                             | `/reset`                           | 起動時フィクスチャのリセット基準を復元し、ランタイム状態をすべてクリアします（`200` でスナップショットを返します）。                                                                                                                |
| `GET` / `DELETE`                   | `/history`                         | 直近 200 件のプロトコルリクエストを返します（`200`、古い順）。`DELETE` ではクリアします（`204`）。                                                                                                                                  |
| `POST`                             | `/users`                           | ユーザーを作成します（`name`、`email`、省略可能な `id`）。`201` を返します。ID がすでにある場合は `409 duplicate` を返します。                                                                                                      |
| `PATCH` / `DELETE`                 | `/users/{id}`                      | ユーザーを編集（`name`、`email`。`id` は変更不可）または削除（`204`）します。ユーザーを削除すると、そのユーザーが所有するデータも削除されます。                                                                                     |
| `POST`                             | `/calendars`                       | カレンダーを作成します（`userId`、`summary`、省略可能な `timeZone`、`primary`、`id`）。`201` を返します。                                                                                                                           |
| `PATCH` / `DELETE`                 | `/calendars/{id}`                  | カレンダーを編集または削除（`204`）します。`id` と `userId` は変更できません。                                                                                                                                                      |
| `GET` / `POST`                     | `/calendars/{id}/events`           | イベントの一覧取得、またはイベントの作成（`200`）を行います。一覧取得では `syncToken` を含む `events.list` のパラメーターを使えます。一覧の各項目には `calendarId` が入ります。                                                     |
| `GET` / `PUT` / `PATCH` / `DELETE` | `/calendars/{id}/events/{eventId}` | イベントの取得、置き換え、部分更新、削除（`204`。削除済みレコードは残ります）を行います。                                                                                                                                           |
| `POST`                             | `/connections/{id}/revoke`         | 接続のトークンを取り消し、その接続の watch チャネルを停止します（`204`）。                                                                                                                                                          |
| `POST`                             | `/deliveries/drain`                | 待機中の Webhook 配信とそのリトライが終わるまで待ち、配信ログの配列を返します（`200`）。                                                                                                                                            |

### 連鎖的な削除と管理 API からの書き込み

- **ユーザーの削除:** ユーザーを削除すると、そのユーザーの OAuth 接続が取り消され、watch チャネルも停止します。ユーザーのカレンダーとイベントも削除されます。このとき、カレンダーの削除済みレコードは作られません。
- **カレンダーの削除とプライマリフラグ:** ユーザーの最初のカレンダーは、自動的に `primary: true` になります。同じユーザーの別のカレンダーに `primary: true` を設定すると、フラグはそのカレンダーに一度で移ります。`primary` を直接外そうとすると `400` が返ります。カレンダーを削除すると、次の処理が行われます。
  - そのカレンダーのイベントを削除し、イベントの watch チャネルを停止します。
  - デフォルトのリスト設定で `calendarList` の削除済みレコードを記録します。`summaryOverride` や `colorId` などのユーザーごとのカスタマイズは消えます。
  - 削除したカレンダーがプライマリカレンダーだった場合は、所有者の別のカレンダーをプライマリにします。このとき、所有者のカレンダーリストに残っているカレンダーが優先されます。
- **カレンダーリストの通知:** 管理 API でカレンダーを作成（`POST /calendars`）、編集（`PATCH /calendars/{id}`）、削除すると、そのたびに所有者の `calendarList.watch` チャネルに `exists` 通知がキューに入ります。編集では、内容が何も変わらなくても通知が送られます。テストで配信数を数える場合は、この分の配信も考慮してください。
- **管理 API からのイベント書き込み:** `/__calendarpit/calendars/{id}/events` でのイベントの書き込みには、招待者に関する制限がかかりません。`conferenceDataVersion=1` も不要です。読み取り専用のフィールド（`organizer`、`creator`、`iCalUID`、`recurringEventId`、`originalStartTime`）も設定できます。更新時には、保存済みの `organizer`、`creator`、`iCalUID` が保持されます。イベントにすでに `recurringEventId` と `originalStartTime` がある場合は、それらも更新時に保持されます。

## リセットとフィクスチャ読み込みの違い

`POST /__calendarpit/reset` と `POST /__calendarpit/fixtures` は、どちらも保存データを置き換えてすぐに保存し、ランタイム状態をすべてクリアします。違いは読み込むデータです。

| 項目                                         | `POST /__calendarpit/reset` | `POST /__calendarpit/fixtures`                                    |
| -------------------------------------------- | --------------------------- | ----------------------------------------------------------------- |
| ユーザー、カレンダー、イベント、クライアント | 起動時の状態から復元        | 送信した[フィクスチャ JSON](/calendarpit/ja/fixtures/) で置き換え |
| 起動時のリセット基準                         | 変わらない                  | 変わらない（次の `/reset` では元の起動時のデータが復元されます）  |
| ランタイム状態                               | クリア                      | クリア                                                            |

`POST /__calendarpit/fixtures` の検証は、すべて成功するかすべて失敗するかのどちらかです。無効なレコードが 1 件でもあれば、Calendarpit は `400` を返し、何も変更しません。

どちらのエンドポイントも、有効な [watch チャネル](/calendarpit/ja/watch/)をすべて停止し、送信中のリクエストを中断します。さらに、次のものをクリアします。

- OAuth 接続、アクセストークンとリフレッシュトークン、認可コード、処理中の同意
- リクエスト履歴
- [同期トークン](/calendarpit/ja/sync/)と、イベントおよびカレンダーリストのページトークン
- カレンダーの削除済みレコード
- ユーザーごとのカレンダーリスト設定（`calendarList.insert`/`patch`/`update` によるカスタマイズと、`calendarList.delete` による削除）
- 招待の通知と、すべての配信ログレコード

どちらかを呼び出した後は、古いアクセストークンは `401`（`authError`）、古い同期トークンは `410`（`fullSyncRequired`）で失敗します。リセットしても、SQLite のデータベースファイルは削除されず、ディスク上のフィクスチャファイルも変更されません。

## リクエスト履歴と状態のエクスポート

`GET /__calendarpit/history` は、`/calendar/v3/*`、`/oauth*`、`/userinfo` で処理した直近 200 件のリクエストを古い順に返します。`401` や `501` などの失敗したリクエストも含まれます。

Calendarpit は、履歴の中の認証情報を次のようにマスクします。

- 次のキーの値は `"[REDACTED]"` に置き換えられます: `authorization`、`cookie`、`set-cookie`、`client_secret`、`secret`、`access_token`、`refresh_token`、`id_token`、`code`、`code_verifier`、`code_challenge`、`consent`、`token`、`x-goog-channel-token`、`state`。ヘッダー、ボディ、クエリ文字列、`Location` や `Referer` の URL が対象です。
- URL に含まれる認証情報は削除されます。
- 12,000 文字を超える文字列は途中で切られ、末尾に ` [truncated]` が付きます。

`GET /__calendarpit/state` は確認用です。その出力を `POST /__calendarpit/fixtures` で読み込み直すことはできません。理由は次のとおりです。

- クライアントのシークレットが含まれません。`clients` には `id` と `redirectUris` だけが入ります。
- チャネルのトークンは `"[REDACTED]"` と表示されます。
- ランタイムのフィールド（`storage`、`connections`、`channels`、`deliveries`、`notifications`、`revision`）が含まれます。`POST /__calendarpit/fixtures` はこれらを `400`（`unsupportedFeature`）で拒否します。
- カレンダーリストの設定は含まれません。設定は `calendarList.list`/`get` で取得してください。

データの投入や再読み込みには、元のフィクスチャファイルを残しておいて使ってください。

## 再現可能なテストの書き方

- **シナリオごとにリセットする:** 各テストの前に `POST /__calendarpit/reset` を呼び出して、起動時の状態に戻します。特定のフィクスチャを読み込みたい場合は、代わりに `POST /__calendarpit/fixtures` を呼び出します。
- **固定の ID を使う:** フィクスチャファイルで、ユーザー、カレンダー、イベント、クライアントに `id` を明示してください。ID がない場合、Calendarpit はデータ投入時に一度だけ ID を生成します。`:memory:` モードでは、サーバープロセスを起動するたびに新しい ID が生成されます。
- **並列ワーカーを分離する:** テストワーカーごとに、`--port 0` と `--database :memory:` を付けて Calendarpit のプロセスを 1 つずつ起動します。ワーカーごとに別の SQLite ファイルを使う方法もあります。
- **ポートは標準出力から読み取る:** `--port 0` を使う場合は、起動時の行 `Admin  http://127.0.0.1:<port>/` から URL を読み取ります。たとえば `/Admin\s+(http:\/\/[^\s]+)/` でマッチできます。その後、`GET /__calendarpit/health` が応答するまでポーリングしてから、テストを始めてください。
- **スリープではなく Webhook 配信をドレインする:** `POST /__calendarpit/deliveries/drain` は、呼び出した時点で待機中の配信を、リトライも含めて終わるまで待ちます。`/reset` は送信中の Webhook リクエストを中断します。ただし、中断される前に受信側がそのリクエストを受け取っている場合があります。
- **再起動後は状態を取得し直す:** [SQLite での再起動](/calendarpit/ja/storage/)をテストする場合、停止前にキューに入っていた配信は `cancelled` になり、再送されません。再起動後に、カレンダーの状態をもう一度取得してください。

```ts
const baseUrl = 'http://127.0.0.1:4173';
const jsonHeaders = { 'Content-Type': 'application/json' };

export async function resetCalendarpit() {
  const res = await fetch(`${baseUrl}/__calendarpit/reset`, {
    method: 'POST',
    headers: jsonHeaders,
    body: '{}',
  });
  if (!res.ok) throw new Error(`Reset failed: ${res.status}`);
  return res.json();
}

export async function drainDeliveries() {
  const res = await fetch(`${baseUrl}/__calendarpit/deliveries/drain`, {
    method: 'POST',
    headers: jsonHeaders,
    body: '{}',
  });
  if (!res.ok) throw new Error(`Drain failed: ${res.status}`);
  return res.json();
}
```
