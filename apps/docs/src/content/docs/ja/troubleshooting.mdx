リクエストが失敗すると、Calendarpit は明示的なステータスコードとエラーメッセージを返します。未対応のフィールドやパラメーターを黙って無視することはありません。

原因を調べるときは、管理画面の **API history** (`http://127.0.0.1:4173/history`) を開きます。直近 200 件の Calendar API と OAuth のやり取りを確認できます。各エントリには HTTP メソッド、パス、ステータスコード、ヘッダー、マスク済みのリクエストボディとレスポンスボディが記録されます。**Errors** トグルを使うと、ステータスが `400` 以上のレスポンスだけを表示できます。

## エラーレスポンスの形式

Calendar API のルート (`/calendar/v3/*`)、`/userinfo`、管理 API のルート (`/__calendarpit/*`) は、Google API と同じ形式でエラーを返します。

```json
{
  "error": {
    "code": 404,
    "message": "Event not found.",
    "errors": [
      {
        "domain": "calendarpit",
        "reason": "notFound",
        "message": "Event not found."
      }
    ]
  }
}
```

- トップレベルのエラーでは、`domain` は常に `"calendarpit"` です。`freebusy.query` レスポンスの中のカレンダーごとのエラーは `"domain": "global"` になります。
- `401` レスポンスには `WWW-Authenticate: Bearer` ヘッダーが付きます。
- より具体的な reason がない `400` の検証エラーは `"reason": "invalidParameter"` になります。

OAuth のルート (`/oauth/*` と `/oauth2/*`) は OAuth のエラー形式を返します。ほとんどのエラーは HTTP `400` です。未実装のパスは `501`、保留中の同意リクエストが多すぎる場合は `429`、別オリジンから同意画面を送信した場合は `403` を返します。

```json
{
  "error": "invalid_grant",
  "error_description": "Invalid, expired, or mismatched authorization code."
}
```

`GET /oauth/authorize` の検証エラーは、HTTP `400` の JSON としてブラウザーに直接返ります。Calendarpit は不正な認可リクエストを `redirect_uri` にリダイレクトしません。

## Calendarpit の起動

CLI で起動に失敗すると、`stderr` に `Calendarpit: <message>` を出力し、終了コード `1` で終了します。Docker の出力は `docker compose logs calendarpit` で確認できます。

| 症状                                                                                | 考えられる原因                                                                                              | 対処                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Calendarpit: Failed to start server. | `Calendarpit: Database is already in use: <path>. Use a separate path or :memory:.` | 別のプロセスが同じ SQLite ファイルをロックしています。                                                      | 別のプロセスを停止するか、プロセスごとに異なる `--database` のパスまたは `:memory:` を使います。[ストレージと再起動](/calendarpit/ja/storage/)を参照してください。                                         |
| `Calendarpit: ENOENT: no such file or directory, open '<path>'`                     | フィクスチャのパスが作業ディレクトリ内、またはコンテナ内に存在しません。                                    | 正しい絶対パスを指定します。Docker ではファイルをマウントし、コンテナ内のパスを渡します。[フィクスチャ](/calendarpit/ja/fixtures/)を参照してください。                                                     |

| オプションの値が不正、未知のオプションやコマンド                                    | 不正なフラグ、空の値、未対応のサブコマンドを指定しています。                                                | `calendarpit --help` で確認します。サブコマンドは `serve` のみです。ポートは `0` から `65535` の整数で指定します。                                                                                         |

| `invalid_grant`: `Invalid, expired, or mismatched authorization code.` | 認可コードが発行から 60 秒を過ぎている、すでに 1 回使われている、`redirect_uri` がないか `/oauth/authorize` のときと違う、クライアントが違う、接続が取り消された、またはサーバーが再起動しました。                                                                                          | `/oauth/authorize` で使ったものと同じ `redirect_uri` とクライアントで、60 秒以内に 1 回だけ交換します。                                                                                                       |
| `invalid_grant`: `Invalid PKCE verifier.`                              | `code_verifier` が `S256` の `code_challenge` と一致しないか、`[A-Za-z0-9._~-]` の 43〜128 文字になっていません。                                                                                                                                                                           | `S256` のチャレンジを計算したときの元の verifier 文字列を送ります。                                                                                                                                           |
| `invalid_grant`: `Invalid refresh token.`                              | 接続が取り消された、ユーザーが削除された、ワークスペースがリセットされたかフィクスチャが読み込まれた、インメモリのサーバーが再起動した、またはトークンが別のクライアントのものである、のいずれかです。                                                                                      | 認可フローをやり直して、新しい接続を作ります。                                                                                                                                                                |

| `invalid_scope`: `Unsupported or missing scope.`                       | `scope` が空か、未対応のスコープ (`calendar.events.owned` や Drive のスコープなど) を含んでいます。                                                                                                                                                                                         | [対応しているスコープ](/calendarpit/ja/oauth/) だけを要求します。                                                                                                                                             |
| `invalid_scope`: `Refresh scope changes are unsupported.`              | `refresh_token` リクエストに `scope` パラメーターが含まれており、その値が最初に付与されたときの文字列 (スコープの順序を含む) と完全には一致していません。                                                                                                                                   | トークンを更新するときは `scope` を省略します。                                                                                                                                                               |
| トークンレスポンスに `refresh_token` がない                            | `/oauth/authorize` で `access_type=offline` を送っていません。または、`refresh_token` グラントのレスポンスです (更新のレスポンスは新しい `access_token` だけを返します。元のリフレッシュトークンは有効なままです)。                                                                         | `/oauth/authorize` に `access_type=offline` を追加し、最初に受け取った `refresh_token` を保存しておきます。                                                                                                   |
| `/oauth/authorize` で `unsupported_feature` になる                     | リクエストに `prompt=none`、`include_granted_scopes=true`、または `nonce`、`login_hint`、`hd`、`enable_granular_consent` などの未対応のパラメーターが含まれています。                                                                                                                       | 未対応のパラメーターを外し、対話的な同意 (`prompt=consent` か `prompt=select_account`) を使います。                                                                                                           |
| `invalid_request`: `PKCE requires S256.` / `Missing PKCE challenge.`   | `code_challenge_method=S256` なしで `code_challenge` を送った (`plain` の場合も含む)、`code_challenge` なしで `code_challenge_method` を送った、または `code_challenge` が 43 文字の base64url になっていません。                                                                           | `code_challenge_method=S256` と、43 文字の base64url のチャレンジを使います。                                                                                                                                 |
| `invalid_request`: `Consent request expired or already used.`          | 同意画面を 5 分を超えて開いたままにした、2 回送信した、または送信前にサーバーが再起動しました。                                                                                                                                                                                             | `/oauth/authorize` から新しい認可リクエストを始めます。                                                                                                                                                       |
| `429 rateLimitExceeded`: `Too many pending consent requests.`          | 保留中の同意リクエストがすでに 1,000 件あります。各リクエストは 5 分で期限切れになります。通常はテスト内のループが原因です。                                                                                                                                                                | 同意リクエストを完了させるか、新しく開くのをやめます。またはワークスペースをリセットします。                                                                                                                  |

## 差分同期とページネーション

| 症状                                                                                                                                                     | 考えられる原因                                                                                                                                                                                                                                                                             | 対処                                                                                                                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `410 fullSyncRequired`: `Sync token is invalid or expired. Perform a full synchronization.`                                                              | `syncToken` が 7 日より古い、破棄された (ワークスペース内のトークンが 100 個を超えた)、別のカレンダーやユーザーのものである、またはリセット、フィクスチャの読み込み、インメモリでの再起動で消えた、のいずれかです。                                                                        | ローカルの同期状態を破棄し、`syncToken` なしの `events.list` でフル同期をやり直します。詳しくは [差分同期](/calendarpit/ja/sync/) を参照してください。         |
| `400`: `Sync query options must match the initial synchronization.`                                                                                      | `singleEvents`、または実際に使われる `timeZone` が最初の同期と違います (`timeZone` を省略していて、カレンダーのタイムゾーンが変わった場合も含みます)。                                                                                                                                     | 最初のフル同期と同じ `singleEvents` と `timeZone` を指定します。                                                                                               |
| `400`: `<key> cannot be combined with syncToken.` / `Incremental synchronization must include deleted events.` / `instances does not support syncToken.` | `syncToken` を `timeMin`、`timeMax`、`orderBy`、`updatedMin`、`iCalUID`、または拡張プロパティのフィルターと一緒に送った、`showDeleted=false` と一緒に送った、または `events.instances` で使った、のいずれかです。                                                                          | `events.list` には `syncToken` だけを送ります。一緒に送れるのは、最初と同じ `singleEvents` と `timeZone`、`maxResults`、`pageToken`、`showDeleted=true` です。 |
| `410 invalidPageToken`: `Invalid or expired page token.` / `Invalid or stale page token.`                                                                | イベントの `pageToken` が期限切れになった (有効期間 1 時間)、破棄された (固定されたページが 1,000 を超えた)、クエリのオプションが変わった、またはサーバーの再起動やリセットがありました。または、ワークスペースのデータに書き込みがあった後に `calendarList` の `pageToken` を使いました。 | 最初のページから一覧を取得し直します。                                                                                                                         |

## watch 通知

| 症状                                                                                                                      | 考えられる原因                                                                                                                                                                                                                                                                                                                                                                                   | 対処                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `400`: `Watch host is not allowed. Configure CALENDARPIT_WATCH_HOSTS explicitly.`                                         | コールバックの `address` のホスト名が、`127.0.0.1`、`[::1]`、`localhost` のいずれでもありません (`host.docker.internal` やコンテナのサービス名など)。                                                                                                                                                                                                                                            | `CALENDARPIT_WATCH_HOSTS=<host1>,<host2>` (ホスト名のみ、ポートなし) を設定して Calendarpit を起動します。詳しくは [watch 通知](/calendarpit/ja/watch/) を参照してください。                                       |
| `400`: `Invalid watch callback URL.`                                                                                      | `address` が `http:` でも `https:` でもないか、認証情報や `#fragment` を含んでいます。                                                                                                                                                                                                                                                                                                           | 認証情報やフラグメントを含まない `http://` か `https://` のコールバック URL を使います。                                                                                                                           |
| `400`: `Only web_hook channels are supported.` / `Invalid channel ID.` / `Invalid channel token.` / `Invalid expiration.` | `type` が `"web_hook"` ではない、`id` が `[A-Za-z0-9_-]{1,64}` に一致しない、`token` が 256 文字を超えるか改行を含む、または `expiration` が未来の Unix ミリ秒の整数ではない、のいずれかです。                                                                                                                                                                                                   | `events.watch` か `calendarList.watch` のリクエストボディで、不正なフィールドを直します。                                                                                                                          |
| `409 duplicate`: `Duplicate channel ID.`                                                                                  | ワークスペース内の別の有効な watch チャネルが、すでにその `id` を使っています。                                                                                                                                                                                                                                                                                                                  | チャネルごとに新しい一意の `id` (UUID など) を生成します。                                                                                                                                                         |
| watch は成功するが、お使いのアプリに通知が届かない                                                                        | Webhook の受信側に接続できなかった、2,000 ms 以内に応答しなかった、または `200`、`201`、`202`、`204` 以外のステータスを返しました (3xx のリダイレクトはたどりません)。3 回試しても失敗すると、その配信は `failed` になります。                                                                                                                                                                   | 管理画面の **Watch** (`http://127.0.0.1:4173/watch`) で、配信ログの状態と HTTP ステータスコードを確認します。テストでは `POST /__calendarpit/deliveries/drain` を呼び、待機中の配信が終わるまで待ちます。          |
| 再起動、リセット、取り消しの後に通知が届かなくなる                                                                        | 再起動すると、キューにある配信は取り消されます。インメモリでの再起動ではチャネルも消えます。コールバックのホストが許可されなくなった状態で再起動した場合も、チャネルは消えます。リセット、フィクスチャの読み込み、接続の取り消しではチャネルが停止します。カレンダーを削除すると、そのカレンダーのイベントのチャネルも停止します。また、チャネルには期限があります (既定は 24 時間、最大 7 日)。 | 再起動の後は状態を取得し直します。チャネルが停止したか期限切れになっている場合は、新しい watch チャネルを登録します。                                                                                              |
| `channels.stop` で `404 notFound`: `Channel not found.`                                                                   | `resourceId` が違う、チャネル ID が存在しない、チャネルがすでに停止したか期限切れ後に削除されている、またはチャネルを作成した接続とは別の接続のトークンで `channels.stop` を呼びました。                                                                                                                                                                                                         | チャネルを作成した接続のトークンと、一致する `resourceId` で `channels.stop` を呼びます。期限切れでも、まだ削除されていないチャネルには `204` が返ります。[watch 通知](/calendarpit/ja/watch/)を参照してください。 |
