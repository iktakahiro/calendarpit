リクエストが失敗した場合、Calendarpit は未対応のフィールドやパラメータを黙って無視せず、明示的なステータスコードとエラーメッセージを返します。

管理画面の **API history**（`http://127.0.0.1:4173/history`）を開くと、直近 200 件の Calendar API と OAuth の通信を確認できます。各履歴には HTTP メソッド、パス、ステータスコード、ヘッダー、マスク処理されたリクエストおよびレスポンスのボディが記録されます。**Errors** トグルを使うと、ステータスコードが `400` 以上のレスポンスだけに絞り込めます。

## エラーレスポンスの形式

Calendar API のルート（`/calendar/v3/*`）、`/userinfo`、および管理 API のルート（`/__calendarpit/*`）は、Google API 形式のエラーオブジェクトを返します。

```json
{
  "error": {
    "code": 404,
    "message": "Event not found.",
    "errors": [
      {
        "domain": "calendarpit",
        "reason": "notFound",
        "message": "Event not found."
      }
    ]
  }
}
```

- トップレベルのエラーでは、`domain` はすべて `"calendarpit"` です。`freebusy.query` レスポンス内のカレンダーごとのエラーでは `"domain": "global"` が使われます。
- `401` レスポンスには `WWW-Authenticate: Bearer` ヘッダーが含まれます。
- 個別の理由が定義されていない `400` バリデーションエラーでは、`"reason": "invalidParameter"` が使われます。

OAuth のルート（`/oauth/*` および `/oauth2/*`）は、OAuth のエラー形式を返します。ほとんどのエラーは HTTP `400` です。未実装のパスは `501`、保留中の同意リクエストが多すぎる場合は `429`、クロスオリジンからの同意送信は `403` を返します。

```json
{
  "error": "invalid_grant",
  "error_description": "Invalid, expired, or mismatched authorization code."
}
```

`GET /oauth/authorize` でのバリデーションエラーは、ブラウザに HTTP `400` の JSON として直接返されます。Calendarpit は、不正な認可リクエストを `redirect_uri` へリダイレクトしません。

## Calendarpit の起動

CLI の起動に失敗すると、`stderr` に `Calendarpit: <message>` を出力して終了コード `1` で終了します。`bun run dev` を使った場合、データベース、設定ファイル、フィクスチャのエラーは `Calendarpit:` プレフィックスなしで Vite のログに出力され、リクエストは `500` を返します。ポートが競合している場合は、Vite の `Port 4173 is already in use` が表示されます。

| 症状 | 主な原因 | 対処方法 |
| --- | --- | --- |
| `Calendarpit: Failed to start server. Is port 4173 in use?` | 別のプロセス（2 つ目の Calendarpit インスタンスや `bun run dev` など）がすでにポート `4173` をリッスンしています。 | 別のプロセスを停止するか、`--port <n>` を指定してください。または `--port 0` を指定して OS に空きポートを選択させ、起動時の出力から `Admin` の URL を確認してください。 |
| `Calendarpit: Database is already in use: <path>. Use a separate path or :memory:.` | 別のプロセスが同じ SQLite ファイルの排他ロック（`<path>.lock`）を保持しています（`bun run dev` と `bun run start` でデフォルトのファイルを共有している場合や、並列テストワーカーを実行している場合など）。 | 別のプロセスを停止するか、プロセスごとに異なる `--database <path>` または `--database :memory:` を指定してください。詳しくは[ストレージと再起動](/calendarpit/ja/storage/)を参照してください。 |
| `Calendarpit: Build the application first with "bun run build".` | `dist/` をビルドする前に `bun run start` または `bin/calendarpit.ts` を実行しました。 | 先に `bun run build` を実行してください。 |
| `Calendarpit: ENOENT: no such file or directory, open '<path>'` | `--config` または `CALENDARPIT_CONFIG` のパスが、プロセスの作業ディレクトリからの相対パスとして存在しません。`bun run dev` と `bun run start` は `apps/calendarpit` を作業ディレクトリとして実行されます。 | `"$PWD/fixtures/default.json"` のように絶対パスを渡してください。詳しくは[フィクスチャ](/calendarpit/ja/fixtures/)を参照してください。 |
| `Calendarpit: Each user with calendars must have exactly one primary calendar.` | 起動時フィクスチャの JSON がバリデーションに失敗しています（ユーザーがカレンダーを持っているのに `"primary": true` のカレンダーがない場合など）。 | [フィクスチャのルール](/calendarpit/ja/fixtures/)に合うようにフィクスチャファイルを修正してください。 |
| フィクスチャを編集して再起動しても反映されない | `--config` と `CALENDARPIT_CONFIG` は、新しいデータベースの初期化時にのみ使われます。既存の SQLite ファイルには、保存済みのデータとリセット基準（起動時の状態）がそのまま残ります。 | 現在のデータを置き換えるには、`POST /__calendarpit/fixtures` または管理画面の **Settings → Test data** からフィクスチャを読み込んでください。フィクスチャを読み込んでもリセット基準は変わりません。リセット基準を変更するには、新しい `--database` パスまたは `:memory:` を指定して起動するか、サーバーを停止して SQLite ファイルを削除してください。 |
| `bun run dev` と単体実行ファイルの間でデータが空になる、または内容が異なる | デフォルトのデータベースパス（`.calendarpit/calendarpit.sqlite`）はプロセスの作業ディレクトリからの相対パスです。ワークスペースのスクリプトは `apps/calendarpit` で実行されますが、単体実行ファイルは起動したディレクトリを基準にします。 | `--database` に絶対パスを渡すか、起動時の出力（CLI では `Data <path>`、`bun run dev` では `Calendarpit data: <path>`）および管理画面の **Settings → Test data** を確認してください。 |
| `CALENDARPIT_HOST` または `CALENDARPIT_PORT` が無視される | `bun run dev` では Vite の接続先が `127.0.0.1:4173` に固定されています。 | ホストやポートを変更するには、ビルド済みサーバー（`bun run build && bun run start`）または単体実行ファイルを使用してください。詳しくは[起動と設定](/calendarpit/ja/running/)を参照してください。 |
| `Calendarpit: Port must be an integer between 0 and 65535.` / `Host must not be empty.` / `Database path must not be empty.` / `Config path must not be empty.` | CLI フラグまたは `CALENDARPIT_*` 環境変数に、不正な値または空の値が設定されています。 | フラグまたは環境変数の値を修正してください。 |
| `Calendarpit: Unknown option '--...'`（または他の `Option '--...'` パースエラー） / `Unknown command. Use "calendarpit serve" or "calendarpit --help".` | 未定義の CLI オプション、フラグ引数の不足や曖昧な指定（値なしの `--host` や `--port -1` など）、または未対応のサブコマンド（サブコマンドは `serve` のみ）が指定されています。 | 有効なフラグと値を渡すか、`bun apps/calendarpit/bin/calendarpit.ts --help`（または単体実行ファイルに `--help`）を実行して有効なフラグを確認してください。 |

## OAuth

| 症状 | 主な原因 | 対処方法 |
| --- | --- | --- |
| 本物の Google 同意画面が表示される | お使いのアプリの認可 URL が Google（`accounts.google.com`）を指したままになっています。 | 認可 URL を `http://127.0.0.1:4173/oauth/authorize` に設定してください。詳しくは[アプリの接続](/calendarpit/ja/connect/)を参照してください。 |
| トークン交換やリフレッシュが Google に接続してしまう | OAuth クライアントが Google のトークンエンドポイントを使い続けています。Calendar API のエンドポイントを変更しても、OAuth の通信先は切り替わりません。 | トークン URL を `http://127.0.0.1:4173/oauth/token` に上書きしてください（`/oauth/revoke` や `/userinfo` を使う場合はそれらも上書きします）。詳しくは[ローカル OAuth](/calendarpit/ja/oauth/)を参照してください。 |
| `/oauth2/...` または `/oauth/tokeninfo` で `501 unsupportedFeature` が返る | SDK が Google のデフォルトの OAuth パス（`/oauth2/v4/token`、`/oauth2/v3/userinfo`、`/oauth/tokeninfo`）を呼び出しています。 | エンドポイントを `/oauth/authorize`、`/oauth/token`、`/oauth/revoke`、`/userinfo` に明示的に上書きしてください。 |
| `invalid_request`: `Unregistered redirect URI.` | `redirect_uri` が `clients[].redirectUris` のエントリと完全一致していません（`localhost` と `127.0.0.1` の違い、ポート、パス、末尾のスラッシュの有無など）。`SAMPLE_PORT` を `4175` から変更した場合も、組み込みの `sample-app` クライアントと一致しなくなります。 | フィクスチャの `clients[].redirectUris` に、`redirect_uri` の文字列をそのままコピーして登録してください。 |
| `invalid_client`: `Unknown client.` | `client_id` がフィクスチャに登録されていないか、`POST /oauth/token` が `application/x-www-form-urlencoded` ではなく JSON ボディで送信されています（クライアントが HTTP Basic 認証を使っている場合は `unsupported_grant_type` が返ります）。 | フィクスチャにクライアントを登録し、トークンリクエストは `application/x-www-form-urlencoded` で送信してください。 |
| `invalid_client`: `Invalid client secret.` | `client_secret` が指定されていないか、間違っています。Calendarpit では、PKCE フローを含めすべてのトークンリクエストでクライアントシークレットが必要です。 | 一致する `client_secret` をフォームボディまたは HTTP Basic 認証で送信してください。 |
| `invalid_grant`: `Invalid, expired, or mismatched authorization code.` | 認可コードの発行から 60 秒以上経過した、すでに 1 回使用された、`redirect_uri` が未指定または `/oauth/authorize` の時と異なる、クライアントが異なる、連携が失効した、またはサーバーが再起動しました。 | `/oauth/authorize` で使用したものと完全に同じ `redirect_uri` とクライアントを使い、60 秒以内に 1 回だけ認可コードを交換してください。 |
| `invalid_grant`: `Invalid PKCE verifier.` | `code_verifier` が `S256` の `code_challenge` と一致しないか、`[A-Za-z0-9._~-]` の 43〜128 文字になっていません。 | `S256` チャレンジの計算に使った元の verifier 文字列を送信してください。 |
| `invalid_grant`: `Invalid refresh token.` | 連携の失効、ユーザーの削除、ワークスペースのリセット、フィクスチャの読み込み、インメモリサーバーの再起動が行われたか、別のクライアントに属するトークンです。 | 認可フローをもう一度実行して、新しい連携を作成してください。 |
| コールバックで `state` が欠落している、または一致しない | `/oauth/authorize` で `state` を省略したか（送信された場合のみそのまま返されます）、お使いのアプリを `localhost` で開いて `127.0.0.1` でコールバックを受け取りました（アプリが `state` を Cookie に保存している場合、ホスト名が異なると Cookie が送信されません）。 | `/oauth/authorize` に `state` を渡し、お使いのアプリと `redirect_uri` の両方で同じホスト名（`127.0.0.1` または `localhost`）を使用してください。 |
| `invalid_scope`: `Unsupported or missing scope.` | `scope` が空であるか、未対応のスコープ（`calendar.events.owned` や Drive のスコープなど）が含まれています。 | [対応しているスコープ](/calendarpit/ja/oauth/)のみをリクエストしてください。 |
| `invalid_scope`: `Refresh scope changes are unsupported.` | `refresh_token` リクエストに含まれる `scope` パラメータが、元の認可時のスコープ文字列と（順序を含めて）完全一致していません。 | トークンをリフレッシュする際は `scope` を省略してください。 |
| トークンレスポンスに `refresh_token` が含まれない | `/oauth/authorize` で `access_type=offline` を送信していないか、`refresh_token` グラントのレスポンスです（リフレッシュ時のレスポンスは新しい `access_token` のみを返し、元のリフレッシュトークンが引き続き有効です）。 | `/oauth/authorize` に `access_type=offline` を追加し、最初に発行された `refresh_token` を保持してください。 |
| `/oauth/authorize` で `unsupported_feature` が返る | リクエストに `prompt=none`、`include_granted_scopes=true`、または未対応のパラメータ（`nonce`、`login_hint`、`hd`、`enable_granular_consent` など）が含まれています。 | 未対応のパラメータを削除し、対話型の同意（`prompt=consent` または `prompt=select_account`）を使用してください。 |
| `invalid_request`: `PKCE requires S256.` / `Missing PKCE challenge.` | `code_challenge_method=S256` なしで `code_challenge` を送信した（`plain` を含む）、`code_challenge` なしで `code_challenge_method` を送信した、または `code_challenge` が 43 文字の base64url 文字列ではありません。 | `code_challenge_method=S256` と 43 文字の base64url チャレンジを使用してください。 |
| `invalid_request`: `Consent request expired or already used.` | 同意画面を開いたまま 5 分以上経過した、2 回送信された、または送信前にサーバーが再起動しました。 | `/oauth/authorize` から新しい認可リクエストを開始してください。 |
| `429 rateLimitExceeded`: `Too many pending consent requests.` | 保留中の同意リクエストがすでに 1,000 件に達しています（各リクエストは 5 分で期限切れになります。主にテストのループが原因で発生します）。 | 同意リクエストを完了または停止するか、ワークスペースをリセットしてください。 |

## Calendar API と SDK

| 症状 | 主な原因 | 対処方法 |
| --- | --- | --- |
| `401 authError`: `Invalid or expired access token.` | `Authorization: Bearer` ヘッダーの欠落または形式不正、アクセストークンの期限切れ（有効期間 1 時間）、連携の失効、ワークスペースのリセットやフィクスチャの読み込み、インメモリサーバーの再起動、または本物の Google トークンの送信が原因です。 | `/oauth/token` でトークンをリフレッシュするか、リセット・フィクスチャ読み込み・失効の後は再度認可を行ってください。 |
| `403 insufficientPermissions`: `Insufficient scope.` | トークンに必要なスコープがありません（`.readonly` スコープでのイベント書き込み、`calendar.events` のみでの `calendarList.list` 呼び出し、`openid`・`email`・`profile` なしでの `/userinfo` 呼び出しなど）。 | エンドポイントに必要なスコープをリクエストして再度認可を行ってください。詳しくは[ローカル OAuth](/calendarpit/ja/oauth/)を参照してください。 |
| `501 unsupportedFeature`: `Unsupported API endpoint or method.`（`/calendar/v3/calendar/v3/...` のようにパスが重複している場合を含む） | 未実装の Google エンドポイント（`acl`、`settings`、`colors`、`calendars.insert`、`events.move`）を呼び出した、API パスに `HEAD` を送信した（イベントのパスは `HEAD` に `405 methodNotAllowed` を返し、`/calendars/{calendarId}` は `Unsupported calendar operation.` を返します）、またはベース URL の設定ミスで SDK が `/calendar/v3` を重複させています。 | [Calendar API 互換性](/calendarpit/ja/compatibility/)を確認してください。JS/TS（`@googleapis/calendar`）では `rootUrl` を `http://127.0.0.1:4173/` に設定します。Java では `rootUrl` にオリジンを、`servicePath` に `calendar/v3/` を設定します。Python、Go、C# ではベース URL に `/calendar/v3/` を含めてください。詳しくは[SDK の使用例](/calendarpit/ja/sdks/)を参照してください。 |
| `501 unsupportedFeature`: `Unsupported calendar operation.` | `/calendar/v3/calendars/{calendarId}` に対して `PUT`、`PATCH`、`DELETE`、または `HEAD` を呼び出しました。 | カレンダーの管理は管理画面または `/__calendarpit/calendars` から行ってください。詳しくは[テスト制御 API](/calendarpit/ja/test-control/)を参照してください。 |
| `404 notFound`: `Calendar not found.` | 存在しないカレンダー ID、別のテストユーザーが所有するカレンダー、またはカレンダーを持たないユーザーの `primary` を指定しました。 | 認証中のユーザーが所有するカレンダー ID を使うか、そのカレンダーの所有者として認可を行ってください。 |
| `404 notFound`: `Event not found.` | 対象カレンダーに存在しないイベント ID を指定したか、`POST .../events/import` または（`text` なしの）`POST .../events/quickAdd` を呼び出して `import` や `quickAdd` がイベント ID として扱われました。 | イベント ID を確認し、`import` や `quickAdd` の代わりに `events.insert` を使用してください。 |
| `405 methodNotAllowed`: `Unsupported event method.` / `Unsupported instances operation.` | イベントのルートに対して無効な HTTP メソッド（`HEAD`、`/events` への `DELETE`、既存の `/events/{eventId}` への `POST`、`/instances` への書き込みなど）を使用しました。 | 対応している HTTP メソッドとパスを使用してください。 |
| `400 unsupportedFeature`: `Unsupported query parameter: <key>` | エンドポイントで許可されていないクエリパラメータ（`fields`、`q`、`eventTypes`、`sendNotifications`、`supportsAttachments`、`maxAttendees`、`text` など）が指定されています。 | 該当するパラメータを削除し、SDK が自動で付与する部分レスポンス用の `fields` マスクを無効にしてください。 |
| `400 unsupportedFeature`: `Unsupported field: <key>` | リクエストボディに未対応のフィールド（イベントの `eventType`、`attachments`、`source`、`htmlLink` や、FreeBusy の `items[]` 内の `id` 以外のキーなど）が含まれています。 | リクエストを送信する前に未対応のフィールドを取り除いてください。詳しくは[Calendar API 互換性](/calendarpit/ja/compatibility/)を参照してください。 |
| `400 invalidParameter`: `Only JSON responses are supported.` | クエリに `alt=media` または `alt=proto` が含まれています。 | `alt` を省略するか、`alt=json` を使用してください。 |
| `400`: `Expected an RFC3339 timestamp with an offset.` / `dateTime requires an offset or timeZone.` | `timeMin`、`timeMax`、`updatedMin`、または FreeBusy の期間指定に `Z` や `±HH:MM` がないか、イベントの `dateTime` にオフセットと `timeZone` の両方がありません。 | `Z` または `±HH:MM` オフセットを付けるか、イベントの `start`/`end` に `timeZone` を指定してください。 |
| `400`: `Invalid or ambiguous local time; supply an explicit offset.` | オフセットなしの `dateTime` が、`timeZone` における夏時間（DST）の空白期間または重複期間に入っています。 | `dateTime` に明示的な数値オフセットを含めてください。 |
| `400`: `Recurring timed events require start.timeZone.` / `Timed recurrence UNTIL must be UTC.` | 時刻指定の繰り返しイベントに `start.timeZone` がないか、`UNTIL` の値が `Z` で終わっていません。 | `start.timeZone` を設定し、時刻指定イベントの `UNTIL` タイムスタンプは UTC（`...Z`）で記述してください。詳しくは[イベント・繰り返し・時刻](/calendarpit/ja/recurrence/)を参照してください。 |
| 繰り返しルールまたは展開処理での `400 unsupportedFeature` | ルールに `HOURLY`/`MINUTELY`、未対応の指定（`BYHOUR`、`BYWEEKNO`、`BYYEARDAY`）、他の iCalendar 行（`DTSTART`）、夏時間の空白期間に当たる回、終了条件なしで `timeMax` を指定しない展開、または 10,000 インスタンスもしくは 100 年を超える展開が含まれています。 | 対応している `DAILY`、`WEEKLY`、`MONTHLY`、`YEARLY` ルールを使用し、`timeMax`（およびより狭い期間）を指定してください。詳しくは[イベント・繰り返し・時刻](/calendarpit/ja/recurrence/)を参照してください。 |
| `400`: `startTime ordering requires singleEvents=true.` | `singleEvents=true` なしで `orderBy=startTime` が送信されました。 | `events.list` のクエリに `singleEvents=true` を追加してください。 |
| `400`: `Event is not a recurring series.` | 繰り返しではないイベントに対して `events.instances` を呼び出しました。 | `events.instances` は繰り返しの系列の親イベントに対してのみ呼び出してください。 |
| `400`: `<key> is read-only.` | Calendar API の書き込みで `organizer`、`creator`、`iCalUID`、`recurringEventId`、または `originalStartTime` を変更しようとしました。 | 該当フィールドを省略するか、既存の値を変更せずにそのまま送信してください。主催者のメタデータを個別に設定したい場合は、[フィクスチャ](/calendarpit/ja/fixtures/)または[テスト制御 API](/calendarpit/ja/test-control/)を使用してください。 |
| `400`: `conferenceData requires conferenceDataVersion=1.` | `?conferenceDataVersion=1` なしで、イベントのペイロードに `conferenceData` を含めました。 | クエリ文字列に `conferenceDataVersion=1` を追加してください。 |
| `403 forbiddenForNonOrganizer` | 招待された参加者（招待コピーの編集者）が `PUT` を使用した、共有イベントのフィールドを変更した、または他の参加者の情報を編集しました。 | `PATCH` を使用し、自身の `responseStatus`/`comment`、`reminders`、`colorId`、`transparency`、または `extendedProperties` のみを更新してください。 |
| `409 duplicate`: `Duplicate event ID.` / `Invitation event ID conflicts with an existing local event.` | `events.insert` でそのカレンダー内の既存 ID を再利用したか、参加者の招待コピーが参加者のプライマリカレンダーにある「同じ ID で `iCalUID` が異なるイベント」（フィクスチャやテスト制御 API で設定されたものなど）を上書きしようとしました。同じ ID でもデフォルトの `iCalUID` を持つイベントは、招待コピーによって上書きされます。 | 一意のイベント ID を使用してください。 |
| `410 deleted`: `Event is already deleted.` | すでに `cancelled` 状態のイベントに対して `events.delete` を呼び出しました。 | 削除時の `410` は削除済みとして扱ってください。 |
| `412 conditionNotMet`: `Event has changed.` | `If-Match` ヘッダーがイベントの現在の `etag` と一致していません。 | `events.get` でイベントを再取得してからリトライしてください。 |
| `413 payloadTooLarge`: `Request body too large.` | リクエストボディが 1,048,576 バイト（1 MiB）を超えています。 | ペイロードのサイズを小さくしてください。 |
| `400`: `maxResults must be between 1 and 2500.` | `maxResults` が `0`、負の値、または `2500` を超えています。 | `maxResults` は `1` から `2500` の間で設定してください。 |
| Python SDK が Google からディスカバリドキュメントを取得しようとする | `googleapiclient.discovery.build` がディスカバリメタデータを Google からダウンロードしようとしました。 | `google-api-python-client` 2.x で `static_discovery=True` と `cache_discovery=False` を指定し、リモートのディスカバリ URL は設定しないでください。詳しくは[SDK の使用例](/calendarpit/ja/sdks/)を参照してください。 |

## 差分同期とページネーション

| 症状 | 主な原因 | 対処方法 |
| --- | --- | --- |
| `410 fullSyncRequired`: `Sync token is invalid or expired. Perform a full synchronization.` | `syncToken` の発行から 7 日以上経過した、上限超過により破棄された（ワークスペース内で 100 トークン超）、別のカレンダーまたはユーザーのトークンである、あるいはリセット・フィクスチャ読み込み・インメモリ再起動によって消去されました。 | ローカルの同期状態を破棄し、`syncToken` なしで `events.list` のフル同期を実行してください。詳しくは[差分同期](/calendarpit/ja/sync/)を参照してください。 |
| `400`: `Sync query options must match the initial synchronization.` | `singleEvents` または有効な `timeZone`（`timeZone` 省略時にカレンダーのタイムゾーンが変更された場合を含む）が、初回の同期時と異なっています。 | 初回のフル同期時とまったく同じ `singleEvents` と `timeZone` オプションを指定してください。 |
| `400`: `<key> cannot be combined with syncToken.` / `Incremental synchronization must include deleted events.` / `instances does not support syncToken.` | `syncToken` を `timeMin`、`timeMax`、`orderBy`、`updatedMin`、`iCalUID`、または拡張プロパティフィルタと組み合わせた、`showDeleted=false` とともに送信した、あるいは `events.instances` で使用しました。 | `events.list` では `syncToken`（および一致する `singleEvents`、`timeZone`、`maxResults`、`pageToken`、`showDeleted=true`）のみを送信してください。 |
| `410 invalidPageToken`: `Invalid or expired page token.` / `Invalid or stale page token.` | イベントの `pageToken` が期限切れ（有効期間 1 時間）になった、上限超過で破棄された（1,000 ページ超）、クエリオプションが変更された、サーバーが再起動またはリセットされた、あるいはワークスペースのデータ書き込み後に `calendarList` の `pageToken` が使用されました。 | 最初のページから一覧取得をやり直してください。 |

## Watch 通知

| 症状 | 主な原因 | 対処方法 |
| --- | --- | --- |
| `400`: `Watch host is not allowed. Configure CALENDARPIT_WATCH_HOSTS explicitly.` | コールバック `address` のホスト名が `127.0.0.1`、`[::1]`、`localhost` のいずれでもありません（`host.docker.internal` やコンテナのサービス名など）。 | `CALENDARPIT_WATCH_HOSTS=<host1>,<host2>`（ポートを含めないホスト名のみ）を指定して Calendarpit を起動してください。詳しくは[Watch 通知](/calendarpit/ja/watch/)を参照してください。 |
| `400`: `Invalid watch callback URL.` | `address` が `http:` または `https:` ではないか、認証情報や `#fragment` が含まれています。 | 通常の `http://` または `https://` のコールバック URL を使用してください。 |
| `400`: `Only web_hook channels are supported.` / `Invalid channel ID.` / `Invalid channel token.` / `Invalid expiration.` | `type` が `"web_hook"` ではない、`id` が `[A-Za-z0-9_-]{1,64}` に一致しない、`token` が 256 文字を超えているか改行を含む、または `expiration` が未来の Unix ミリ秒の整数ではありません。 | `events.watch` リクエストボディの該当フィールドを修正してください。 |
| `409 duplicate`: `Duplicate channel ID.` | ワークスペース内の別の有効な watch チャネルがすでにその `id` を使用しています。 | チャネルごとに新しい一意の `id`（UUID など）を生成してください。 |
| Watch の登録は成功するが、お使いのアプリに通知が届かない | Webhook の受信先に到達できない、応答に 2,000 ミリ秒以上かかった、または `200`、`201`、`202`、`204` 以外のステータスを返しました（3xx リダイレクトは追跡されません）。3 回試行しても成功しない場合、配信は `failed` になります。 | 管理画面の **Watch**（`http://127.0.0.1:4173/watch`）を開き、配信ログのステータスと HTTP ステータスコードを確認してください。テスト内では `POST /__calendarpit/deliveries/drain` を呼び出して、保留中の配信が完了するまで待機してください。 |
| 再起動、リセット、または失効の後に通知が届かなくなる | 再起動するとキュー内の配信はキャンセルされます。インメモリでの再起動や、再起動後にコールバックのホストが許可されなくなった場合もチャネルは破棄されます。また、リセット、フィクスチャの読み込み、連携の失効、カレンダーの削除によってチャネルは停止します。さらに、チャネルには有効期限（デフォルト 24 時間、最大 7 日間）があります。 | 再起動後はイベントを再取得してください。チャネルが停止または期限切れになった場合は、新しい watch チャネルを登録してください。 |
| `channels.stop` で `404 notFound`: `Channel not found.` が返る | `resourceId` が間違っている、チャネルがすでに停止または期限切れになっている、あるいはチャネルを作成した連携とは別の連携のトークンで `channels.stop` を呼び出しました。 | チャネルを作成した連携のトークンと一致する `resourceId` を使って `channels.stop` を呼び出してください。 |

## 管理 API

| 症状 | 主な原因 | 対処方法 |
| --- | --- | --- |
| `415 unsupportedMediaType`: `Management writes require application/json.` | `/__calendarpit/*` への `POST`、`PATCH`、`PUT`、または `DELETE` リクエスト（`/reset` や `/deliveries/drain` のようなボディなしの呼び出しを含む）が、`Content-Type: application/json` なしで送信されました。 | 管理 API のすべての書き込みリクエストに `-H 'Content-Type: application/json'` を含めてください。詳しくは[テスト制御 API](/calendarpit/ja/test-control/)を参照してください。 |
| `403 forbidden`: `Cross-origin management requests are not allowed.` | 別のオリジンにあるブラウザスクリプトから `/__calendarpit/*` を呼び出しました。 | テストランナー、CLI、またはバックエンドから（クロスオリジンの `Origin` ヘッダーなしで）`/__calendarpit/*` を呼び出すか、管理画面を使用してください。 |
| `POST /__calendarpit/fixtures` で `400 unsupportedFeature`: `Unsupported field: storage` が返る | `GET /__calendarpit/state` のレスポンスをそのままフィクスチャとして送信しました。 | `users`、`calendars`、`events`、`clients`（クライアントの `secret` を含む）のみで構成された有効なフィクスチャオブジェクトを送信してください。詳しくは[フィクスチャ](/calendarpit/ja/fixtures/)を参照してください。 |
