---
title: フィクスチャ
description: JSON のフィクスチャファイルで、テストユーザー、カレンダー、イベント、OAuth クライアントを定義します。
---

フィクスチャは、Calendarpit の初期テストデータを定義する JSON ファイルです。テストユーザー、カレンダー、イベント、OAuth クライアントを定義できます。ローカルサーバーやテストスイートを、決まったデータで起動したいときに使います。

フィクスチャで `id` を明示すると、ユーザー ID、カレンダー ID、イベント ID、OAuth クライアント ID が固定されます。テストのアサーションでは、生成された値を問い合わせずに、決まった ID をそのまま検証できます。

## 起動時にフィクスチャを読み込む

フィクスチャファイルのパスは、CLI フラグ `--config` または環境変数 `CALENDARPIT_CONFIG` で指定します。どちらも指定しない場合、Calendarpit は組み込みのデフォルトフィクスチャを読み込みます。内容はリポジトリの `fixtures/default.json` と同じです。ユーザー `alex` と `sam`、カレンダー `alex-work`、`alex-personal`、`sam-work`、イベント `planning` 1 件、OAuth クライアント `sample-app` が含まれます。

テスト用には `fixtures/default.json` をコピーして編集してください。

```sh
# 方法 1: 開発サーバーを起動する
CALENDARPIT_DATABASE=:memory: CALENDARPIT_CONFIG="$PWD/fixtures/default.json" bun run dev

# 方法 2: ビルドしてサーバーを起動する
bun run build
bun run start -- --database :memory: --config "$PWD/fixtures/default.json" --port 4173
```

`--config` と `CALENDARPIT_CONFIG` のパスは、プロセスの作業ディレクトリからの相対パスとして解釈されます。リポジトリのワークスペーススクリプト（`bun run dev` と `bun run start`）では、アプリケーションが `apps/calendarpit` で実行されます。そのため、`"$PWD/fixtures/default.json"` のような**絶対パス**を指定してください。起動オプションの一覧は [起動と設定](/calendarpit/ja/running/) を参照してください。

起動時フィクスチャが投入されるのは、**新しい空の**データベースだけです。

- `--database :memory:` モードでは、プロセスを起動するたびにデータベースが新しくなります。そのため、フィクスチャは毎回適用されます。
- SQLite ファイルに保存済みのデータがある場合、Calendarpit はフィクスチャを適用せず、警告も表示しません。保存済みのデータ（ユーザーごとのカレンダーリスト設定と、削除済みカレンダーのレコードを含む）と、最初のリセット基準を読み込みます。この場合でも、指定するパスは読み取り可能な JSON ファイルを指している必要があります。そうでない場合は起動に失敗します。ファイルの内容は検証されません。詳しくは [ストレージと再起動](/calendarpit/ja/storage/) を参照してください。

実行中に別のフィクスチャを読み込むには `POST /__calendarpit/fixtures` を使います。テストの合間にリセット基準（起動時の状態）へ戻すには `POST /__calendarpit/reset` を使います。どちらも次のデータを消去します。OAuth の許可とトークン、ユーザーごとのカレンダーリスト設定、削除済みカレンダーのレコード、watch チャネル、配信、リクエスト履歴、同期トークン、通知です。リセットでは起動時フィクスチャが復元されます。カレンダーリストのエントリは、起動時の etag を持つデフォルトの状態で戻ります。`GET /__calendarpit/state` の結果には、クライアントシークレット、カレンダーリスト設定、削除済みレコードが含まれません。そのため、フィクスチャとして読み込み直すことはできません。詳しくは [テスト制御 API](/calendarpit/ja/test-control/) を参照してください。

## ルート構造と例

フィクスチャファイルのルートは JSON オブジェクトである必要があります。使えるキーは `users`、`calendars`、`events`、`clients` の 4 つで、どれも省略できる配列です。空のオブジェクト（`{}`）も有効な空のフィクスチャです。

キーを指定する場合、値は配列にしてください（違反時は `"<key> must be an array."`）。ルートオブジェクト、またはユーザー、カレンダー、イベント、クライアントの各エントリにそれ以外のキーがあると、検証に失敗します（`"Unsupported field: <key>"`、reason は `unsupportedFeature`）。

```json
{
  "users": [{ "id": "alex", "name": "Alex", "email": "alex@example.test" }],
  "calendars": [
    {
      "id": "work",
      "userId": "alex",
      "summary": "Work",
      "timeZone": "Asia/Tokyo",
      "primary": true
    }
  ],
  "events": [
    {
      "id": "meeting",
      "calendarId": "work",
      "summary": "Planning",
      "start": { "dateTime": "2026-10-19T10:00:00+09:00" },
      "end": { "dateTime": "2026-10-19T11:00:00+09:00" }
    }
  ],
  "clients": [
    {
      "id": "sample-app",
      "secret": "local-sample-secret",
      "redirectUris": ["http://127.0.0.1:4175/callback"]
    }
  ]
}
```

## ID のルールと検証

ユーザー、カレンダー、イベント、クライアントの ID は省略できます。ただし、カレンダーを所有するユーザーと、イベントを含むカレンダーには、明示的な `id` が必要です。他のエントリから参照するためです。

- **使える文字**: ASCII の英字、数字、`@`、`.`、`_`、`-` です（`^[a-zA-Z0-9@._-]{1,128}$`）。最大 128 文字です。空文字列、空白だけの文字列、文字列以外の `id` は `"id must be a nonempty string."` で失敗します。空でない文字列がパターンに合わない場合は `"Invalid ID."` で失敗します。129〜10,000 文字の ID は `"Invalid ID."` で失敗し、それより長い値は `"id must be a nonempty string."` で失敗します。
- **予約済み ID**: `primary` は予約されているため、ID には使えません（`"Invalid ID."` で失敗します）。
- **一意性**: `users`、`calendars`、`clients` の ID は、それぞれの中で一意である必要があります（`"Duplicate fixture ID."`）。イベント ID はカレンダーごとに一意である必要があります（`"Duplicate event ID."`）。カレンダーが違えば、同じイベント ID を使えます。
- **生成される ID とリセット基準への記録**: `id` を省略すると、Calendarpit は UUID を生成します。生成された ID とイベントの初期メタデータ（`created`、`updated`、`etag`）は、投入時に起動時のリセット基準として記録されます。そのため、`POST /__calendarpit/reset` を何度呼んでも同じデータが再現されます。SQLite では、このリセット基準がプロセスの再起動後も保持されます。`:memory:` モードでは、新しいプロセスを起動するたびに新しい UUID とタイムスタンプが生成されます。

検証はアトミックに行われます。所有者とカレンダーへの参照は、すべてフィクスチャ内に存在している必要があります。ルールに違反すると、Calendarpit は最初のエラーで処理を止めます。

- 新しいデータベースで起動したとき: `Calendarpit: <message>` を出力し、終了コード `1` で終了します。
- `POST /__calendarpit/fixtures` のとき: `400`（`invalidParameter` または `unsupportedFeature`）を返し、既存のデータは変更しません。

## セクションリファレンス

### `users`

テストユーザーを定義します。テストユーザーは同意画面でアクセスを承認し、カレンダーを所有します。

| フィールド | 必須 | デフォルト | ルール |
| --- | --- | --- | --- |
| `id` | 任意 | 生成された UUID | `[a-zA-Z0-9@._-]` に一致する 1〜128 文字。`primary` は不可。`users` 内で一意。 |
| `name` | 必須 | — | 10,000 文字以内の空でない文字列。 |
| `email` | 必須 | — | `^[^\s@]+@[^\s@]+$` に一致する、10,000 文字以内の空でない文字列（違反時は `"Invalid email."`）。 |

### `calendars`

フィクスチャのユーザーが所有するカレンダーを定義します。カレンダーを所有するユーザーには、`"primary": true` のカレンダーが**ちょうど 1 つ**必要です（違反時は `"Each user with calendars must have exactly one primary calendar."`）。カレンダーが 1 つだけでも、`"primary": true` がなければ検証に失敗します。カレンダーを持たないユーザーも定義できます。そのユーザーでは、`primary` カレンダーエイリアスが `404` を返します。

| フィールド | 必須 | デフォルト | ルール |
| --- | --- | --- | --- |
| `id` | 任意 | 生成された UUID | `[a-zA-Z0-9@._-]` に一致する 1〜128 文字。`primary` は不可。`calendars` 内で一意。 |
| `userId` | 必須 | — | `users` のユーザー `id` と一致すること（違反時は `"Unknown calendar owner."`）。 |
| `summary` | 必須 | — | 10,000 文字以内の空でない文字列。 |
| `timeZone` | 任意 | `"UTC"` | 有効な IANA タイムゾーン名（違反時は `"Invalid IANA time zone."`）。 |
| `primary` | 任意 | `false` | 真偽値（違反時は `"primary must be boolean."`）。 |

投入されたカレンダーは、デフォルト設定（`selected: true`、`colorId: "1"`）で所有者のカレンダーリストに入ります。あとで管理 API でカレンダーやユーザーを変更したときの動作は次のとおりです（[テスト制御 API](/calendarpit/ja/test-control/) を参照）。

- プライマリカレンダーを削除すると、残りの所有カレンダーのうち、カレンダーリストに残っている最初のものが選ばれます。残りのカレンダーがすべてリストから外されている場合は、残りの所有カレンダーの最初のものが選ばれます。選ばれたカレンダーは必要に応じてリストに戻され、その他のリスト設定は保持されます。
- 別のカレンダーに `"primary": true` を設定すると、フラグがアトミックに移ります。そのカレンダーはカレンダーリストに戻され、その他の設定は保持されます。
- カレンダーを削除すると、そのリスト設定は消え、削除済みカレンダーのレコードが記録されます。このレコードは、`showDeleted=true` のときに `deleted: true` とデフォルトのリスト設定で返されます。削除したプライマリカレンダーのレコードは `primary: true` を保持します。削除済みの ID でカレンダーを作り直すと、そのレコードと保存されていたリスト設定は消去されます。
- ユーザーを削除すると、そのユーザーの OAuth の許可が取り消され、watch チャネルも停止します。カレンダー、イベント、リスト設定も削除されます。この場合、削除済みレコードは追加されません。

### `events`

初期イベントを定義します。フィクスチャのイベントには、Calendar API のイベントフィールドと同じ値の検証が適用されます（[Calendar API の互換性](/calendarpit/ja/compatibility/) と [イベント、繰り返し、時刻](/calendarpit/ja/recurrence/) を参照）。これに加えて `calendarId` を指定します。

- 読み取り専用フィールド（`organizer`、`creator`、`iCalUID`、`recurringEventId`、`originalStartTime`）も設定できます。
- `conferenceData` には `conferenceDataVersion` は不要です。
- リクエスト専用フィールドの `attendeesOmitted` は拒否されます（`"Unsupported field: attendeesOmitted"`）。
- 投入時には、API で挿入したときの副作用は実行されません。参加者のカレンダーに招待のコピーは作られません。`conferenceData.createRequest` があっても会議リンクは生成されません。

| フィールド | 必須 | デフォルト | ルール |
| --- | --- | --- | --- |
| `calendarId` | 必須 | — | `calendars` のカレンダー `id` と一致すること（違反時は `"Unknown event calendar."`）。 |
| `id` | 任意 | 生成された UUID | `[a-zA-Z0-9@._-]` に一致する 1〜128 文字。`primary` は不可。カレンダー内で一意。 |
| `start`, `end` | 必須 | — | イベントの開始と終了（`dateTime` または終日イベントの `date`）。ルールは Calendar API と同じ。 |
| `organizer`, `creator`, `iCalUID`, `recurringEventId`, `originalStartTime` | 任意 | カレンダーの所有者（`organizer`、`creator`）、`<id>@calendarpit.local`（`iCalUID`）、なし（`recurringEventId`、`originalStartTime`。両方設定するか、どちらも設定しない） | 通常の API リクエストでは読み取り専用ですが、フィクスチャでは設定できます。たとえば、外部の主催者や、保存済みの繰り返しの例外を投入するときに使います。`recurringEventId` と `originalStartTime` の片方だけを設定すると `"Instances require recurringEventId and originalStartTime."` で失敗します。 |
| `sequence` | 任意 | `0` | 0 以上の整数（違反時は `"Invalid sequence."`）。 |
| `created`, `updated`, `etag` | 無視 | 投入時に生成 | 指定した値は無視され、フィクスチャの投入時に生成されます。 |

### `clients`

[ローカル OAuth](/calendarpit/ja/oauth/) で使う OAuth クライアントを定義します。クライアントごとの `scopes` フィールドはありません。どのクライアントも、対応しているすべてのスコープを要求できます。

| フィールド | 必須 | デフォルト | ルール |
| --- | --- | --- | --- |
| `id` | 任意 | 生成された UUID | `[a-zA-Z0-9@._-]` に一致する 1〜128 文字。`primary` は不可。`clients` 内で一意。 |
| `secret` | 必須 | — | 10,000 文字以内の空でない文字列。 |
| `redirectUris` | 必須 | — | `http` または `https` の絶対 URL（各 10,000 文字以内）の空でない配列。フラグメントと認証情報は含められません。`/oauth/authorize` では完全一致で照合されます。 |
