title: ストレージと再起動
description: Calendarpit がデータを保存する場所、SQLite とインメモリモードの選び方、再起動やリセットの後に残るデータについて説明します。
---

Calendarpit は、デフォルトではワークスペースの状態をローカルの SQLite ファイルに保存します。使い捨てのテストセッションでは、インメモリに保存することもできます。

## ストレージモードの選び方

npm、Homebrew、単体実行ファイルでは、デフォルトで起動したディレクトリ内の `.calendarpit/calendarpit.sqlite` に保存します。プロジェクトのディレクトリから起動すると、そのプロジェクトごとにデータを保持できます。

保存先や `:memory:` は `--database <path>` または `CALENDARPIT_DATABASE` で指定します。CLI フラグは環境変数より優先されます。[インストール](/calendarpit/ja/installation/)で必要な環境と公開状況を確認してください。

```sh
# Temporary E2E session; no database files are written
npx @iktakahiro/calendarpit@0.9.0 serve --database :memory: --port 0

# Choose a persistent workspace
npx @iktakahiro/calendarpit@0.9.0 serve --database ./.calendarpit/manual.sqlite
```

- **SQLite ファイル（デフォルト）:** 状態を変更するリクエストのたびに、また Webhook の配信が終わるたびに変更を保存します。相対パスは作業ディレクトリを基準に解決されます。
- **インメモリ（`:memory:`）:** データベースファイルもロックファイルも書き込みません。プロセスが終了すると、すべての状態が破棄されます。
- **Docker:** イメージは `CALENDARPIT_DATABASE=/data/calendarpit.sqlite` を設定しています。`-v calendarpit-data:/data` で名前付きボリュームをマウントすると、コンテナを削除して作り直してもデータが残ります。一時的なセッションには `-e CALENDARPIT_DATABASE=:memory:` を渡します。[Compose の例](/calendarpit/ja/installation/)も名前付きボリュームを使います。`docker compose down` ではデータが残り、`docker compose down -v` では削除されます。

使用中のストレージモードとパスは、次の場所で確認できます。

- **起動ログ:** CLI は `Data   <absolute-path>`（または `Data   :memory:`）を出力します。サーバーのエントリが読み込まれた時点で `Calendarpit data: <path or :memory:>` も出力します。
- **管理画面:** サイドバーのフッターに `SQLite` または `In-memory` が表示されます。**Settings → Test data** には、モードの説明とパス（または `:memory:`）が表示されます。
- **管理 API:** `GET /__calendarpit/health` は `storage: "sqlite" | "memory"` を返します。`GET /__calendarpit/state` は `storage: { mode, path? }` を返します。

## SQLite の再起動後に残るデータ

Calendarpit のプロセスは、`SIGINT` または `SIGTERM` を受け取ると、処理中の Webhook 配信を中断し、状態を保存してから、データベースのロックを解放します。既存の SQLite ファイルを開き直すと、保存済みのデータが復元され、短時間しか使わないフローの状態は破棄されます。

| 状態                                                                                                | SQLite の再起動後の扱い                                                                                                                  |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| ユーザー、カレンダー、イベント、OAuth クライアント                                                  | 復元されます。イベント ID、タイムスタンプ、etag もそのまま残ります                                                                       |
| カレンダーリストの設定（ユーザーごとの上書き、色、非表示/選択状態、リマインダー、削除したエントリ） | 復元されます。リセットまたはフィクスチャの読み込みで消去されます                                                                         |
| リセット基準（起動時フィクスチャ）                                                                  | 最初の初期データが保持されます。`--config` または `CALENDARPIT_CONFIG` のファイルの内容は無視されます                                    |
| 接続（許可）、アクセストークン、リフレッシュトークン                                                | 復元されます。アクセストークンは元の有効期限のままです。リフレッシュトークンは期限切れになりません。取り消した接続は取り消されたままです |
| watch チャネル                                                                                      | 有効期限内で、接続が有効で、コールバック先のホストが引き続き許可されている場合に復元されます。メッセージ番号も引き継がれます             |
| リクエスト履歴、配信ログ、通知                                                                      | それぞれ最新の 200 件が復元されます                                                                                                      |
| キュー内または処理中の Webhook 配信                                                                 | `cancelled` になります。自動で再送されることはありません                                                                                 |
| 同期トークン、カレンダーの削除済みレコード                                                          | 復元されます。リセットまたはフィクスチャの読み込みで消去されます                                                                         |
| 保留中の同意、認可コード、ページトークン                                                            | 破棄されます（ページトークンは `calendarList` と `events` のカーソルです）。フローまたは一覧の取得をやり直してください                   |

再起動の後は、お使いのアプリでカレンダーの状態を取得し直してください。停止によって途中で止まった [watch 通知](/calendarpit/ja/watch/)の分を、これで反映できます。

## 初期データ、フィクスチャ、リセット

起動時[フィクスチャ](/calendarpit/ja/fixtures/)（`--config`、`CALENDARPIT_CONFIG`、または組み込みのデフォルト）がデータを投入するのは、**新しいデータベースのときだけ**です。

- **既存の SQLite ファイル:** 保存済みのデータと、最初のリセット基準を開き直します。`--config` または `CALENDARPIT_CONFIG` を設定していても、フィクスチャの内容は無視され、既存のデータベースは上書きされません。ただし、指定したファイルは存在していて、有効な JSON である必要があります。
- **インメモリモード:** 起動するたびに新しいデータベースになります。そのため、起動時フィクスチャは毎回適用され、省略した ID も毎回生成し直されます。
- **リセット（`POST /__calendarpit/reset`）:** 再起動をはさんでいても、起動時のリセット基準に戻します。接続、トークン、認可コード、同意、watch チャネル、カレンダーリストの設定、[同期トークン](/calendarpit/ja/sync/)、ページトークン、カレンダーの削除済みレコード、リクエスト履歴、通知、配信を消去し、すぐに保存します。SQLite ファイルを削除したり、フィクスチャのファイルを変更したりはしません。
- **フィクスチャの読み込み（`POST /__calendarpit/fixtures`）:** 現在のデータを置き換え、実行時の状態を消去します。**リセット基準は変わりません。** その後にリセットしても、最初の初期データに戻ります。詳しくは[テスト制御 API](/calendarpit/ja/test-control/)を参照してください。

## ロック、ファイル、並列実行

1 つの SQLite ファイルを同時に使えるのは、1 つの Calendarpit プロセスだけです。Calendarpit は実行中、`<db>.lock` に排他ロックをかけます。同じファイルを使う 2 つ目のプロセスは、起動時に `Database is already in use: <path>. Use a separate path or :memory:.` というエラーで失敗します（CLI ではこの前に `Calendarpit: ` が付きます）。ロックはプロセスの終了時に OS が解放します。クラッシュした場合も同じです。テストを並列に実行する場合は、ワーカーごとに `--database :memory:` を使うか、別々の SQLite ファイルを指定してください。

SQLite は WAL モードで動作します。Calendarpit は実行中、データベースと同じ場所に `<db>-wal`、`<db>-shm`、`<db>.lock`、`<db>.lock-journal` の補助ファイルを作成します。データベース、`-wal`、`-shm`、`.lock` の各ファイルはモード `0600` になります。Calendarpit がデータベース用のディレクトリを作成した場合、そのディレクトリはモード `0700` になります。実行中は補助ファイルをデータベースと同じ場所に置いたままにしてください。データベースファイルをコピーするときは、先にサーバーを停止してください。データベースにはローカルのテスト用認証情報とクライアントシークレットが入っているため、Git には含めないでください。このリポジトリでは、`.calendarpit/` と、`*.sqlite`、`*.sqlite-wal`、`*.sqlite-shm`、`*.sqlite.lock` のパターンが無視されます。`<db>.lock-journal` が無視されるのは `.calendarpit/` の中にある場合だけです。
