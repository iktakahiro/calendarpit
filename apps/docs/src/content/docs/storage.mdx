title: Storage and restarts
description: Where Calendarpit stores data, how to choose between SQLite and in-memory mode, and what persists across restarts and resets.
---

Calendarpit stores workspace state in a local SQLite file by default, or in memory for throwaway test sessions.

## Choosing a storage mode

By default, the CLI and dev server write to `.calendarpit/calendarpit.sqlite` relative to the process working directory. When you run `bun run dev` or `bun run start` from the repository root, the working directory is `apps/calendarpit`, so the default file is `apps/calendarpit/.calendarpit/calendarpit.sqlite`.

Use `--database <path>` or `CALENDARPIT_DATABASE` to choose a file or `:memory:`. CLI flags override environment variables. `bun run dev` does not accept Calendarpit CLI flags, so set `CALENDARPIT_DATABASE` instead (see [Run and configure](/calendarpit/running/)).

```sh
# Temporary E2E session; no files are written
CALENDARPIT_DATABASE=:memory: bun run dev

bun run build
bun run start -- --database :memory: --port 0

# Choose a persistent workspace (use an absolute path with workspace scripts)
bun run start -- --database "$PWD/.calendarpit/manual.sqlite"
```

- **SQLite file (default):** Saves changes after each request that modifies state and after each webhook delivery finishes. Relative paths resolve against the working directory.
- **In-memory (`:memory:`):** Writes no database or lock files. All state is discarded when the process exits.
- **Docker:** The `Dockerfile` sets `CALENDARPIT_DATABASE=/data/calendarpit.sqlite` and declares `/data` as a volume. Mount `-v calendarpit-data:/data` to keep data when the container is removed and re-created (for example with `--rm`), or pass `-e CALENDARPIT_DATABASE=:memory:` for a temporary session (container build and startup validation are still pending).

Check the active storage mode and path in:

- **Startup log:** The CLI prints `Data   <absolute-path>` (or `Data   :memory:`); the CLI and `bun run dev` also print `Calendarpit data: <path or :memory:>` once the server entry loads.
- **Admin UI:** The sidebar footer shows `SQLite` or `In-memory`; **Settings → Test data** describes the mode and shows the path (or `:memory:`).
- **Management API:** `GET /__calendarpit/health` returns `storage: "sqlite" | "memory"`, and `GET /__calendarpit/state` returns `storage: { mode, path? }`.

## What survives a SQLite restart

On `SIGINT` or `SIGTERM`, the CLI (`bun run start` or the standalone executable) aborts in-flight webhook deliveries, saves state, and releases the database lock. Reopening an existing SQLite file restores saved data and drops short-lived flow state:

| State                                                                                            | SQLite restart behavior                                                                                                |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Users, calendars, events, OAuth clients                                                          | Restored, including event IDs, timestamps, and etags                                                                   |
| Calendar-list settings (per-user overrides, colors, hidden/selected, reminders, removed entries) | Restored; cleared by a reset or fixture load                                                                           |
| Reset baseline (startup fixture)                                                                 | Original seed retained; `--config` and `CALENDARPIT_CONFIG` file contents are ignored                                  |
| Connections (grants), access and refresh tokens                                                  | Restored; access tokens keep their original expiry, refresh tokens do not expire, and revoked connections stay revoked |
| Watch channels                                                                                   | Restored if unexpired, the connection is active, and the callback host is still allowed; message numbers are kept      |
| Request history, delivery log, notifications                                                     | Latest 200 entries of each restored                                                                                    |
| Queued or in-flight webhook deliveries                                                           | Marked `cancelled`; never replayed automatically                                                                       |
| Sync tokens, calendar tombstones                                                                 | Restored; cleared by a reset or fixture load                                                                           |
| Pending consents, authorization codes, page tokens                                               | Discarded (`calendarList` and `events` cursors); restart the flow or list query                                        |

After a restart, refetch calendar state in your app to reconcile [watch notifications](/calendarpit/watch/) interrupted by shutdown.

## Seed baseline, fixtures, and reset

A startup [fixture](/calendarpit/fixtures/) (`--config`, `CALENDARPIT_CONFIG`, or the built-in default) seeds **only a new database**:

- **Existing SQLite file:** Reopens saved data and the original baseline. If `--config` or `CALENDARPIT_CONFIG` is set, the file must still exist and contain valid JSON, but its contents are ignored and do not overwrite the database.
- **In-memory mode:** Every start creates a new database, applies the startup fixture, and regenerates any omitted IDs.
- **Reset (`POST /__calendarpit/reset`):** Restores the original startup baseline, even after restarts. It clears connections, tokens, codes, consents, watch channels, calendar-list settings, [sync tokens](/calendarpit/sync/), page tokens, calendar tombstones, request history, notifications, and deliveries, then saves immediately. It does not delete the SQLite file or modify the fixture file.
- **Load fixture (`POST /__calendarpit/fixtures`):** Replaces current data and clears runtime state **without changing the reset baseline**. Subsequent resets still restore the original seed. See [Test control API](/calendarpit/test-control/).

## Locking, files, and parallel runs

Only one Calendarpit process can use a SQLite file at a time. Calendarpit holds an exclusive lock on `<db>.lock` while running; a second process on the same file fails at startup with `Database is already in use: <path>. Use a separate path or :memory:.` (the CLI prefixes this with `Calendarpit: `). The OS releases the lock on exit, including after a crash. Give each parallel test worker `--database :memory:` or a separate SQLite file.

SQLite runs in WAL mode. While running, Calendarpit creates `<db>-wal`, `<db>-shm`, `<db>.lock`, and `<db>.lock-journal` sidecar files next to the database. The database, `-wal`, `-shm`, and `.lock` files use mode `0600`, and any database directory Calendarpit creates uses mode `0700`. Keep sidecar files with the database while running, and stop the server before copying a database file. Keep the database out of Git because it contains local test credentials and client secrets. In this repository, `.calendarpit/` and the `*.sqlite`, `*.sqlite-wal`, `*.sqlite-shm`, and `*.sqlite.lock` patterns are ignored, while `<db>.lock-journal` is ignored only inside `.calendarpit/`.
