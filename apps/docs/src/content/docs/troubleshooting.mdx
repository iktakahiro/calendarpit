title: Troubleshooting
description: Find the cause and fix for common startup, OAuth, Calendar API, sync, watch, and management API errors in Calendarpit.
---

When a request fails, Calendarpit returns an explicit status code and error message instead of silently ignoring unsupported fields or parameters.

Open **API history** (`http://127.0.0.1:4173/history`) in the admin UI to inspect the latest 200 Calendar API and OAuth exchanges. Each entry records the HTTP method, path, status code, headers, and masked request and response bodies. Use the **Errors** toggle to filter for responses with status `400` or higher.

## Error response formats

Calendar API routes (`/calendar/v3/*`), `/userinfo`, and management API routes (`/__calendarpit/*`) return the Google API error envelope:

```json
{
  "error": {
    "code": 404,
    "message": "Event not found.",
    "errors": [
      {
        "domain": "calendarpit",
        "reason": "notFound",
        "message": "Event not found."
      }
    ]
  }
}
```

- `domain` is `"calendarpit"` on all top-level errors. Per-calendar errors inside a `freebusy.query` response use `"domain": "global"`.
- `401` responses include the `WWW-Authenticate: Bearer` header.
- `400` validation errors without a more specific reason use `"reason": "invalidParameter"`.

OAuth routes (`/oauth/*` and `/oauth2/*`) return the OAuth error format. Most errors are HTTP `400`. Unimplemented paths return `501`, too many pending consent requests return `429`, and a cross-origin consent submission returns `403`:

```json
{
  "error": "invalid_grant",
  "error_description": "Invalid, expired, or mismatched authorization code."
}
```

Validation errors on `GET /oauth/authorize` are returned directly in the browser as HTTP `400` JSON. Calendarpit does not redirect invalid authorization requests back to `redirect_uri`.

## Starting Calendarpit

CLI startup failures print `Calendarpit: <message>` to `stderr` and exit with code `1`. With `bun run dev`, database, config-file, and fixture errors appear in the Vite log without the `Calendarpit:` prefix, and requests return `500`. A port conflict shows Vite's `Port 4173 is already in use`.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Calendarpit: Failed to start server. Is port 4173 in use?` | Another process (such as a second Calendarpit instance or `bun run dev`) is already listening on port `4173`. | Stop the other process, pass `--port <n>`, or pass `--port 0` to let the OS choose a free port and read the `Admin` URL from the startup output. |
| `Calendarpit: Database is already in use: <path>. Use a separate path or :memory:.` | Another process holds the exclusive `<path>.lock` lock on the same SQLite file (for example, `bun run dev` and `bun run start` sharing the default file, or parallel test workers). | Stop the other process, or give each process its own `--database <path>` or `--database :memory:`. See [Storage and restarts](/calendarpit/storage/). |
| `Calendarpit: Build the application first with "bun run build".` | You ran `bun run start` or `bin/calendarpit.ts` before building `dist/`. | Run `bun run build` first. |
| `Calendarpit: ENOENT: no such file or directory, open '<path>'` | The `--config` or `CALENDARPIT_CONFIG` path does not exist relative to the process working directory. `bun run dev` and `bun run start` run with `apps/calendarpit` as their working directory. | Pass an absolute path such as `"$PWD/fixtures/default.json"`. See [Fixtures](/calendarpit/fixtures/). |
| `Calendarpit: Each user with calendars must have exactly one primary calendar.` | The startup fixture JSON fails validation (for example, a user has calendars but none has `"primary": true`). | Fix the fixture file so it matches the [fixture rules](/calendarpit/fixtures/). |
| Fixture edits have no effect after restart | `--config` and `CALENDARPIT_CONFIG` only seed a new database. An existing SQLite file keeps its saved data and reset baseline. | Load the fixture via `POST /__calendarpit/fixtures` or **Settings → Test data** in the admin UI to replace current data. Loading a fixture does not change the reset baseline. To change the baseline, start with a new `--database` path or `:memory:`, or stop the server and delete the SQLite file. |
| Data is empty or differs between `bun run dev` and the binary | The default database path (`.calendarpit/calendarpit.sqlite`) is relative to the process working directory. Workspace scripts run in `apps/calendarpit`, while the binary uses the directory where you start it. | Pass an absolute `--database` path, or check the startup output (`Data <path>` in the CLI, `Calendarpit data: <path>` in `bun run dev`) and **Settings → Test data** in the admin UI. |
| `CALENDARPIT_HOST` or `CALENDARPIT_PORT` is ignored | `bun run dev` hard-codes Vite to `127.0.0.1:4173`. | Use the built server (`bun run build && bun run start`) or the standalone executable to change the host or port. See [Run and configure](/calendarpit/running/). |
| `Calendarpit: Port must be an integer between 0 and 65535.` / `Host must not be empty.` / `Database path must not be empty.` / `Config path must not be empty.` | A CLI flag or `CALENDARPIT_*` environment variable has an invalid or empty value. | Fix the flag or environment variable value. |
| `Calendarpit: Unknown option '--...'` (or another `Option '--...'` parse message) / `Unknown command. Use "calendarpit serve" or "calendarpit --help".` | Unrecognized CLI option, missing or ambiguous flag argument (such as `--host` with no value or `--port -1`), or unsupported subcommand (only `serve` exists). | Pass a valid flag and value, or run `bun apps/calendarpit/bin/calendarpit.ts --help` (or the executable with `--help`) to see valid flags. |

## OAuth

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| A real Google consent screen appears | Your app's authorization URL still points to Google (`accounts.google.com`). | Set the authorization URL to `http://127.0.0.1:4173/oauth/authorize`. See [Connect your app](/calendarpit/connect/). |
| Token exchange or refresh contacts Google | Your OAuth client still uses Google's token endpoint. Setting the Calendar API endpoint does not redirect OAuth calls. | Override the token URL to `http://127.0.0.1:4173/oauth/token` (and `/oauth/revoke` and `/userinfo` if used). See [Local OAuth](/calendarpit/oauth/). |
| `501 unsupportedFeature` on `/oauth2/...` or `/oauth/tokeninfo` | Your SDK is calling Google's default OAuth paths (`/oauth2/v4/token`, `/oauth2/v3/userinfo`, or `/oauth/tokeninfo`). | Override the endpoints explicitly to `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`, and `/userinfo`. |
| `invalid_request`: `Unregistered redirect URI.` | `redirect_uri` does not exactly match an entry in `clients[].redirectUris` (including `localhost` vs `127.0.0.1`, port, path, or trailing slash). Changing `SAMPLE_PORT` from `4175` also causes a mismatch with the built-in `sample-app` client. | Copy the exact `redirect_uri` string into `clients[].redirectUris` in your fixture. |
| `invalid_client`: `Unknown client.` | `client_id` is not registered in the fixture, or `POST /oauth/token` was sent with a JSON body instead of `application/x-www-form-urlencoded` (which returns `unsupported_grant_type` if the client authenticates with HTTP Basic). | Register the client in your fixture and send token requests as `application/x-www-form-urlencoded`. |
| `invalid_client`: `Invalid client secret.` | `client_secret` is missing or wrong. Calendarpit requires a client secret on every token request, including PKCE flows. | Send the matching `client_secret` in the form body or via HTTP Basic authentication. |
| `invalid_grant`: `Invalid, expired, or mismatched authorization code.` | The code is older than 60 seconds, was already used once, `redirect_uri` is missing or differs from `/oauth/authorize`, the client differs, the connection was revoked, or the server restarted. | Exchange the code once within 60 seconds with the exact `redirect_uri` and client used at `/oauth/authorize`. |
| `invalid_grant`: `Invalid PKCE verifier.` | `code_verifier` does not match the `S256` `code_challenge` or is not 43–128 characters of `[A-Za-z0-9._~-]`. | Send the original verifier string used to compute the `S256` challenge. |
| `invalid_grant`: `Invalid refresh token.` | The connection was revoked, the user was deleted, the workspace was reset or a fixture was loaded, an in-memory server restarted, or the token belongs to another client. | Run the authorization flow again to create a new connection. |
| `state` is missing or mismatches on callback | `state` was omitted from `/oauth/authorize` (it is echoed only when sent), or your app started on `localhost` and received the callback on `127.0.0.1` (if your app keeps `state` in a cookie, a callback on a different hostname does not receive it). | Pass `state` on `/oauth/authorize` and use the same hostname (`127.0.0.1` or `localhost`) for both your app and its `redirect_uri`. |
| `invalid_scope`: `Unsupported or missing scope.` | `scope` is empty or includes an unsupported scope (such as `calendar.events.owned` or Drive scopes). | Request only [supported scopes](/calendarpit/oauth/). |
| `invalid_scope`: `Refresh scope changes are unsupported.` | A `refresh_token` request included a `scope` parameter that does not exactly match the original grant string (including scope order). | Omit `scope` when refreshing a token. |
| No `refresh_token` in the token response | `access_type=offline` was not sent on `/oauth/authorize`, or the response is from a `refresh_token` grant (refresh responses return a new `access_token` only; the original refresh token stays valid). | Add `access_type=offline` to `/oauth/authorize` and keep the initial `refresh_token`. |
| `unsupported_feature` on `/oauth/authorize` | The request included `prompt=none`, `include_granted_scopes=true`, or an unsupported parameter such as `nonce`, `login_hint`, `hd`, or `enable_granular_consent`. | Remove unsupported parameters and use interactive consent (`prompt=consent` or `prompt=select_account`). |
| `invalid_request`: `PKCE requires S256.` / `Missing PKCE challenge.` | `code_challenge` was sent without `code_challenge_method=S256` (including `plain`), `code_challenge_method` was sent without `code_challenge`, or `code_challenge` is not 43 base64url characters. | Use `code_challenge_method=S256` with a 43-character base64url challenge. |
| `invalid_request`: `Consent request expired or already used.` | The consent page was left open longer than 5 minutes, submitted twice, or the server restarted before submission. | Start a fresh authorization request at `/oauth/authorize`. |
| `429 rateLimitExceeded`: `Too many pending consent requests.` | 1,000 consent requests are already pending (each expires after 5 minutes; usually caused by a loop in tests). | Complete or stop opening consent requests, or reset the workspace. |

## Calendar API and SDKs

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `401 authError`: `Invalid or expired access token.` | Missing or malformed `Authorization: Bearer` header, access token expired (1-hour TTL), connection revoked, workspace reset or fixture loaded, in-memory server restarted, or a real Google token was sent. | Refresh the token at `/oauth/token`, or authorize again after a reset, fixture load, or revocation. |
| `403 insufficientPermissions`: `Insufficient scope.` | The token lacks a required scope (for example, writing events with a `.readonly` scope, calling `calendarList.list` with only `calendar.events`, or calling `/userinfo` without `openid`, `email`, or `profile`). | Request a scope that covers the endpoint and re-authorize. See [Local OAuth](/calendarpit/oauth/). |
| `501 unsupportedFeature`: `Unsupported API endpoint or method.` (including doubled `/calendar/v3/calendar/v3/...` paths) | You called an unimplemented Google endpoint (`acl`, `settings`, `colors`, `calendars.insert`, `events.move`), sent `HEAD` to an API path (event paths answer `HEAD` with `405 methodNotAllowed`, and `/calendars/{calendarId}` returns `Unsupported calendar operation.`), or your SDK doubled `/calendar/v3` because the base URL was misconfigured. | Check [Calendar API compatibility](/calendarpit/compatibility/). For JS/TS (`@googleapis/calendar`), set `rootUrl` to `http://127.0.0.1:4173/`. For Java, set `rootUrl` to the origin and `servicePath` to `calendar/v3/`. For Python, Go, and C#, include `/calendar/v3/`. See [SDK examples](/calendarpit/sdks/). |
| `501 unsupportedFeature`: `Unsupported calendar operation.` | You called `PUT`, `PATCH`, `DELETE`, or `HEAD` on `/calendar/v3/calendars/{calendarId}`. | Manage calendars in the admin UI or via `/__calendarpit/calendars`. See [Test control API](/calendarpit/test-control/). |
| `404 notFound`: `Calendar not found.` | Unknown calendar ID, a calendar owned by a different test user, or `primary` for a user with no calendars. | Use a calendar ID owned by the authenticated user, or authorize as that calendar's owner. |
| `404 notFound`: `Event not found.` | Unknown event ID in that calendar, or a call to `POST .../events/import` or `POST .../events/quickAdd` (without `text`), where `import` or `quickAdd` is treated as an event ID. | Check the event ID, and use `events.insert` instead of `import` or `quickAdd`. |
| `405 methodNotAllowed`: `Unsupported event method.` / `Unsupported instances operation.` | Invalid HTTP verb for the event route (such as `HEAD`, `DELETE` on `/events`, `POST` on an existing `/events/{eventId}`, or a write to `/instances`). | Use the supported HTTP method and path. |
| `400 unsupportedFeature`: `Unsupported query parameter: <key>` | Query parameter is not on the endpoint allowlist (such as `fields`, `q`, `eventTypes`, `sendNotifications`, `supportsAttachments`, `maxAttendees`, or `text`). | Remove the parameter and disable automatic `fields` partial-response masks in your SDK. |
| `400 unsupportedFeature`: `Unsupported field: <key>` | Request body contains an unsupported field (such as `eventType`, `attachments`, `source`, or `htmlLink` on events, or an `items[]` entry with keys other than `id` on FreeBusy). | Strip unsupported fields before sending the request. See [Calendar API compatibility](/calendarpit/compatibility/). |
| `400 invalidParameter`: `Only JSON responses are supported.` | Query included `alt=media` or `alt=proto`. | Omit `alt` or use `alt=json`. |
| `400`: `Expected an RFC3339 timestamp with an offset.` / `dateTime requires an offset or timeZone.` | `timeMin`, `timeMax`, `updatedMin`, or FreeBusy bounds lack `Z` or `±HH:MM`, or an event `dateTime` has neither an offset nor `timeZone`. | Add `Z` or a `±HH:MM` offset, or supply `timeZone` on the event `start`/`end`. |
| `400`: `Invalid or ambiguous local time; supply an explicit offset.` | An offset-less `dateTime` falls inside a DST gap or overlap in `timeZone`. | Include an explicit numeric offset on `dateTime`. |
| `400`: `Recurring timed events require start.timeZone.` / `Timed recurrence UNTIL must be UTC.` | A timed recurring event has no `start.timeZone`, or its `UNTIL` value does not end with `Z`. | Set `start.timeZone` and write timed `UNTIL` timestamps in UTC (`...Z`). See [Events, recurrence and time](/calendarpit/recurrence/). |
| `400 unsupportedFeature` on recurrence rules or expansion | Rule uses `HOURLY`/`MINUTELY`, an unsupported part (`BYHOUR`, `BYWEEKNO`, `BYYEARDAY`), another iCalendar line (`DTSTART`), a DST-gap occurrence, an unbounded rule without `timeMax`, or an expansion exceeding 10,000 instances or 100 years. | Use supported `DAILY`, `WEEKLY`, `MONTHLY`, or `YEARLY` rules and supply `timeMax` (and a narrower window). See [Events, recurrence and time](/calendarpit/recurrence/). |
| `400`: `startTime ordering requires singleEvents=true.` | `orderBy=startTime` was sent without `singleEvents=true`. | Add `singleEvents=true` to the `events.list` query. |
| `400`: `Event is not a recurring series.` | `events.instances` was called on a non-recurring event. | Call `events.instances` only on recurring series masters. |
| `400`: `<key> is read-only.` | A Calendar API write changed `organizer`, `creator`, `iCalUID`, `recurringEventId`, or `originalStartTime`. | Omit the field or send the existing value unchanged. To set custom organizer metadata, use [Fixtures](/calendarpit/fixtures/) or the [Test control API](/calendarpit/test-control/). |
| `400`: `conferenceData requires conferenceDataVersion=1.` | Event payload includes `conferenceData` without `?conferenceDataVersion=1`. | Add `conferenceDataVersion=1` to the query string. |
| `403 forbiddenForNonOrganizer` | An invitee (editing an invitation copy) used `PUT`, changed shared event fields, or edited another attendee. | Use `PATCH` and update only your own `responseStatus`/`comment`, `reminders`, `colorId`, `transparency`, or `extendedProperties`. |
| `409 duplicate`: `Duplicate event ID.` / `Invitation event ID conflicts with an existing local event.` | `events.insert` reused an existing ID in that calendar, or an attendee invitation copy would replace an event in the attendee's primary calendar that has the same ID but a different `iCalUID` (for example, one set through a fixture or the Test control API). An event with the same ID and the default `iCalUID` is overwritten by the invitation copy. | Use a unique event ID. |
| `410 deleted`: `Event is already deleted.` | `events.delete` was called on an event that is already `cancelled`. | Treat `410` on delete as already deleted. |
| `412 conditionNotMet`: `Event has changed.` | The `If-Match` header does not match the event's current `etag`. | Re-fetch the event with `events.get` and retry. |
| `413 payloadTooLarge`: `Request body too large.` | Request body exceeds 1,048,576 bytes (1 MiB). | Reduce the payload size. |
| `400`: `maxResults must be between 1 and 2500.` | `maxResults` is `0`, negative, or greater than `2500`. | Set `maxResults` between `1` and `2500`. |
| Python SDK fetches discovery documents from Google | `googleapiclient.discovery.build` tried to download discovery metadata from Google. | Use `google-api-python-client` 2.x with `static_discovery=True` and `cache_discovery=False`, and do not set a remote discovery URL. See [SDK examples](/calendarpit/sdks/). |

## Incremental sync and pagination

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `410 fullSyncRequired`: `Sync token is invalid or expired. Perform a full synchronization.` | The `syncToken` is older than 7 days, was evicted (more than 100 tokens in the workspace), belongs to another calendar or user, or was cleared by a reset, fixture load, or in-memory restart. | Discard local sync state and run a full `events.list` without `syncToken`. See [Incremental sync](/calendarpit/sync/). |
| `400`: `Sync query options must match the initial synchronization.` | `singleEvents` or the effective `timeZone` (including a calendar time zone change when `timeZone` was omitted) differs from the initial sync. | Repeat the exact `singleEvents` and `timeZone` options from the initial full sync. |
| `400`: `<key> cannot be combined with syncToken.` / `Incremental synchronization must include deleted events.` / `instances does not support syncToken.` | `syncToken` was combined with `timeMin`, `timeMax`, `orderBy`, `updatedMin`, `iCalUID`, or extended property filters, sent with `showDeleted=false`, or used on `events.instances`. | Send only `syncToken` (plus matching `singleEvents`, `timeZone`, `maxResults`, `pageToken`, or `showDeleted=true`) on `events.list`. |
| `410 invalidPageToken`: `Invalid or expired page token.` / `Invalid or stale page token.` | An event `pageToken` expired (1-hour TTL), was evicted (over 1,000 frozen pages), query options changed, or the server restarted or reset; or a `calendarList` `pageToken` was used after any workspace data write. | Restart listing from the first page. |

## Watch notifications

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `400`: `Watch host is not allowed. Configure CALENDARPIT_WATCH_HOSTS explicitly.` | The callback `address` hostname is not `127.0.0.1`, `[::1]`, or `localhost` (for example, `host.docker.internal` or a container service name). | Start Calendarpit with `CALENDARPIT_WATCH_HOSTS=<host1>,<host2>` (hostnames only, without ports). See [Watch notifications](/calendarpit/watch/). |
| `400`: `Invalid watch callback URL.` | `address` is not `http:` or `https:`, or includes credentials or a `#fragment`. | Use a plain `http://` or `https://` callback URL. |
| `400`: `Only web_hook channels are supported.` / `Invalid channel ID.` / `Invalid channel token.` / `Invalid expiration.` | `type` is not `"web_hook"`, `id` does not match `[A-Za-z0-9_-]{1,64}`, `token` exceeds 256 characters or contains newlines, or `expiration` is not a future Unix millisecond integer. | Fix the invalid field in the `events.watch` request body. |
| `409 duplicate`: `Duplicate channel ID.` | Another active watch channel in the workspace already uses that `id`. | Generate a new unique `id` (such as a UUID) for each channel. |
| Watch succeeds, but no notifications arrive at your app | Your webhook receiver was unreachable, took more than 2,000 ms, or returned a status other than `200`, `201`, `202`, or `204` (3xx redirects are not followed). After 3 attempts, the delivery is marked `failed`. | Check **Watch** (`http://127.0.0.1:4173/watch`) in the admin UI to inspect the delivery log status and HTTP status code. In tests, call `POST /__calendarpit/deliveries/drain` to wait for pending deliveries. |
| Notifications stop arriving after restart, reset, or revocation | Restarting cancels queued deliveries. An in-memory restart also drops channels, and so does a restart where the callback host is no longer allowed. Resetting, loading a fixture, revoking the connection, or deleting the calendar stops channels; channels also expire (default 24 hours, max 7 days). | Re-fetch events after a restart; if the channel was stopped or expired, register a new watch channel. |
| `404 notFound`: `Channel not found.` on `channels.stop` | Wrong `resourceId`, the channel already stopped or expired, or `channels.stop` was called with a token from a different connection than the one that created the channel. | Call `channels.stop` with the creating connection's token and matching `resourceId`. |

## Management API

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `415 unsupportedMediaType`: `Management writes require application/json.` | A `POST`, `PATCH`, `PUT`, or `DELETE` request to `/__calendarpit/*` (including bodyless calls like `/reset` or `/deliveries/drain`) was sent without `Content-Type: application/json`. | Include `-H 'Content-Type: application/json'` on every management write request. See [Test control API](/calendarpit/test-control/). |
| `403 forbidden`: `Cross-origin management requests are not allowed.` | A browser script on another origin called `/__calendarpit/*`. | Call `/__calendarpit/*` from your test runner, CLI, or backend (without a cross-origin `Origin` header), or use the admin UI. |
| `400 unsupportedFeature`: `Unsupported field: storage` on `POST /__calendarpit/fixtures` | You posted a `GET /__calendarpit/state` response directly as a fixture. | Post a valid fixture object containing only `users`, `calendars`, `events`, and `clients` (with client `secret` values). See [Fixtures](/calendarpit/fixtures/). |
