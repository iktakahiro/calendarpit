Calendarpit serves the API, OAuth, and admin UI from one origin.

The commands below use the packaged distribution. You need no source checkout or build. See [Installation](/installation/) for prerequisites and supported platforms.

## Ways to run Calendarpit

### Docker and Compose

```sh
docker run --rm \
  -p 127.0.0.1:4173:4173 \
  -v calendarpit-data:/data \
  ghcr.io/iktakahiro/calendarpit:latest
```

The container has these defaults:

- It runs as a non-root user.
- It sets `CALENDARPIT_HOST=0.0.0.0` and `CALENDARPIT_PORT=4173`.
- It stores the SQLite database at `/data/calendarpit.sqlite`.

The published host port stays on loopback. Add environment variables with `-e` before the image name. Add CLI flags after it:

```sh
docker run --rm -p 127.0.0.1:4173:4173 \
  ghcr.io/iktakahiro/calendarpit:latest serve --database :memory:
```

Related pages:

- [Installation](/installation/): a Compose service, health checks, and host/container addresses.
- [Fixtures](/fixtures/): mount a startup configuration.
- [Development guide](https://github.com/iktakahiro/calendarpit/blob/main/docs/development.md): source development instructions.

### Installed CLI

Install with Homebrew or place a standalone executable on your `PATH`. Then run it from your project directory. See [Installation](/installation/) for setup.

```sh
calendarpit serve --port 4173
calendarpit serve --port 0 --database :memory:
```

These are alternative startup commands:

- Run one server per database file.
- Port `0` lets the OS choose an available port.
- Read the actual URLs in the startup output:

```text
Calendarpit data: :memory:

Calendarpit v<version>
Data   :memory:
Admin  http://127.0.0.1:38425/
API    http://127.0.0.1:38425/calendar/v3
Health http://127.0.0.1:38425/__calendarpit/health
```

The packaged executable includes the server, the admin UI assets (including `favicon.svg`), and the Bun runtime. You need no separate Node.js or Bun installation. Stop the server with Ctrl+C.

## Command-line options and environment variables

The CLI syntax is `calendarpit [serve] [options]`. The `serve` subcommand is optional.

The CLI prints an error to `stderr` and exits with code `1` on any of these:

- an unknown command
- an unknown flag
- an invalid option value

Command-line flags take precedence over environment variables.

| CLI option            | Environment variable     | Default                           | Description                                                                                                           |
| --------------------- | ------------------------ | --------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `--host <host>`       | `CALENDARPIT_HOST`       | `127.0.0.1`                       | Bind address. Non-loopback addresses (`0.0.0.0`, `::`) must be set explicitly.                                        |
| `-p`, `--port <n>`    | `CALENDARPIT_PORT`       | `4173`                            | Listen port (`0`–`65535`). Use `0` to let the OS choose a free port.                                                  |
| `--database <path>`   | `CALENDARPIT_DATABASE`   | `.calendarpit/calendarpit.sqlite` | SQLite database file path, or `:memory:` for a disposable in-memory session. See [Storage and restarts](/storage/).   |
| `--config <path>`     | `CALENDARPIT_CONFIG`     | Built-in fixture                  | Path to a JSON startup fixture. See [Fixtures](/fixtures/).                                                           |
| `--rate-limit <mode>` | `CALENDARPIT_RATE_LIMIT` | `off`                             | Calendar API quota simulation: `off`, `prod`, or `strict`. See [Calendar API rate limits](#calendar-api-rate-limits). |
| `-h`, `--help`        | —                        | —                                 | Print help and exit.                                                                                                  |
| `-v`, `--version`     | —                        | —                                 | Print the version and exit.                                                                                           |

Option details:

- **`--port 0`**: The assigned port appears in the startup output.
- **Port `4175`**: Avoid it if you also run the reference sample app.
- **`--config`**: The file must exist and contain valid JSON. It seeds a new database or a `:memory:` session.

<Callout type="warn">

`--config` is silently ignored when Calendarpit opens an existing SQLite file.

</Callout>

### Additional environment variables

| Environment variable      | Default       | Description                                                                                         |
| ------------------------- | ------------- | --------------------------------------------------------------------------------------------------- |
| `CALENDARPIT_WATCH_HOSTS` | Loopback only | Comma-separated extra hostnames allowed as `events.watch` and `calendarList.watch` webhook targets. |

About `CALENDARPIT_WATCH_HOSTS`:

- Example: `host.docker.internal` when running in Docker.
- It is an environment variable only. There is no CLI flag.
- See [Watch notifications](/watch/).

### Calendar API rate limits

Calendarpit can answer Calendar API requests with the same quota errors Google returns, so an app can exercise that path locally. The default is `off`: requests are not limited.

Set the mode with `--rate-limit` or `CALENDARPIT_RATE_LIMIT`, or in **Settings → Developer**. Accepted values are `off`, `prod`, and `strict`. The mode is saved in the workspace and kept across SQLite restarts. On startup, an explicit flag or environment variable replaces the saved mode and is written back. When neither is set, Calendarpit keeps the saved mode, or `off` when the snapshot has none.

Reset and fixture load keep the mode and clear the in-memory counters. Counters also clear when the mode changes, and they are not restored after a process restart.

Every `/calendar/v3` request counts, including events, `calendarList`, `freeBusy`, and watch. OAuth, `/userinfo`, and `/__calendarpit` do not. `quotaUser` or `x-goog-quota-user` (1–40 characters) selects the per-user bucket and overrides the access token's user. Otherwise the token's user is used, or one shared anonymous bucket when there is no token. A request that does not fit is rejected and is not counted. The response includes `Retry-After`.

Prod follows the Calendar API quotas Google publishes for Cloud projects created on or after 1 May 2026 ([Usage limits](https://developers.google.com/workspace/calendar/api/guides/quota)):

| Limit                          | Prod            | Error                       |
| ------------------------------ | --------------- | --------------------------- |
| Per minute per user            | 600 requests    | `403 userRateLimitExceeded` |
| Per minute per project         | 10,000 requests | `429 rateLimitExceeded`     |
| Writes per minute per calendar | 60 requests     | `403 rateLimitExceeded`     |

Quotas use a sliding minute. The published 1,000,000 requests per day is a billing threshold, not a rejection, so prod does not fail at that number. Google also says writes to one calendar in quick succession can be limited, without a published figure. Prod uses 60 writes per minute per calendar for that operational limit.

Strict is lower, so the same errors are easy to hit:

| Limit                          | Strict      | Error                       |
| ------------------------------ | ----------- | --------------------------- |
| Per minute per user            | 4 requests  | `403 userRateLimitExceeded` |
| Per minute per project         | 12 requests | `429 rateLimitExceeded`     |
| Writes per minute per calendar | 2 requests  | `403 rateLimitExceeded`     |
| Per day per project            | 20 requests | `403 quotaExceeded`         |

The daily ceiling is checked first, then per-calendar writes, then the per-user minute, then the project minute. Error bodies use Google's `usageLimits` domain ([Handle API errors](https://developers.google.com/workspace/calendar/api/guides/errors)):

```json
{
  "error": {
    "code": 403,
    "message": "User Rate Limit Exceeded",
    "errors": [
      {
        "domain": "usageLimits",
        "reason": "userRateLimitExceeded",
        "message": "User Rate Limit Exceeded"
      }
    ]
  }
}
```

`rateLimitExceeded` uses the message `Rate Limit Exceeded`. `quotaExceeded` uses `Calendar usage limits exceeded.`

### Loopback binding and working directory

**Loopback by default.** Calendarpit binds to `127.0.0.1` unless you pass `--host` or `CALENDARPIT_HOST`.

<Callout type="warn">

The admin UI and [test control API](/test-control/) have no authentication. Binding to `0.0.0.0` exposes them to other machines on your network.

</Callout>

**Relative paths.** Path resolution depends on how you run Calendarpit:

- **Homebrew and standalone executables**: Paths in `--database` and `--config` (or their environment variables) resolve from the directory where you start Calendarpit. Run it from your project directory or use absolute paths.
- **Docker**: Paths are inside the container. Mount host files before referencing them.

See [Troubleshooting](/troubleshooting/) for common startup errors.

## Admin UI

The admin UI is served at the root of the same origin as the API. The default URL is `http://127.0.0.1:4173/`. It shows the workspace, request history, and webhook deliveries, and lets you edit test data. See [Admin UI](/admin-ui/).
