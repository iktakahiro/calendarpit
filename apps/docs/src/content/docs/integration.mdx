## Start the two applications

Run these commands in separate terminals:

```sh
bun run dev
bun run sample:dev
```

Calendarpit runs at `http://127.0.0.1:4173`. The separate sample application runs
at `http://127.0.0.1:4175`. Open the sample, choose **Connect calendar**, select a
test user on Calendarpit's consent page, and approve. Select a calendar, start a
watch, then create, update, and delete an event. Use **Refresh state** to inspect
saved events, busy intervals, and received notifications.

The sample defaults to October 19, 2026. Its busy query covers that UTC day.
The admin schedule initially shows October 19 so the built-in planning event is
visible. The sample is a single-connection local demo, not a production session
management example.

## Override every provider endpoint

Changing the Calendar SDK URL alone is not enough. Configure these separately:

| Purpose                   | Local endpoint                          |
| ------------------------- | --------------------------------------- |
| Authorization screen      | `http://127.0.0.1:4173/oauth/authorize` |
| Code exchange and refresh | `http://127.0.0.1:4173/oauth/token`     |
| User profile              | `http://127.0.0.1:4173/userinfo`        |
| Calendar API root         | `http://127.0.0.1:4173/`                |
| Token revocation          | `http://127.0.0.1:4173/oauth/revoke`    |

The JavaScript Calendar SDK appends `/calendar/v3/...` to `rootUrl`; do not include
that path twice. Other SDKs expect a full service URL; see [SDK examples](/calendarpit/sdks/).
A watch address points in the opposite direction: from Calendarpit
to the consuming app, such as `http://127.0.0.1:4175/notifications`.

Starting Calendarpit does not intercept Google traffic. Add a provider switch to
your application's OAuth and Calendar client factories. Environment variable
names such as `CALENDARPIT_URL` are application conventions, not settings that
Google SDKs discover automatically. Use Calendarpit tokens with the local
provider and keep real Google credentials in the Google configuration.

## Complete local OAuth

This flow applies to every language. No Google Cloud project is required.

1. Register a test client in the startup fixture's `clients` array. Its
   `redirectUris` must contain your application's exact callback URL. The
   built-in `sample-app` client only allows `http://127.0.0.1:4175/callback`.
2. Send the browser to `/oauth/authorize` on Calendarpit with `client_id`,
   `redirect_uri`, `response_type=code`, a fresh random `state`, and
   `scope=https://www.googleapis.com/auth/calendar email profile`. Request
   `access_type=offline` if you need a refresh token. Encode query values.
3. The user selects a test account and approves or denies access. In your
   callback, verify `state` against the value stored for that browser session
   before using the code. Handle `error=access_denied` without attempting a code
   exchange.
4. Exchange the code at Calendarpit's `/oauth/token`. Codes expire quickly and
   can only be exchanged once. Store the returned credentials in your app's
   local test session.
5. Pass the returned `access_token` to a Calendar SDK configured for Calendarpit.
   Use [the language examples](/calendarpit/sdks/) to list calendars and query FreeBusy.

The following HTTP examples represent requests made by your application's
backend. Set `PIT_CLIENT_ID`, `PIT_CLIENT_SECRET`, `PIT_REDIRECT_URI`, and
`PIT_CODE` to that client's values and the code received by **its own callback**.
Do not reuse a code already exchanged by the bundled sample. If you use PKCE,
also send the matching `code_verifier` in the exchange.

Refresh before the token's `expires_in` lifetime elapses and update the SDK's
credentials. If the connection has been revoked or the workspace reset, repeat
authorization. Configure any SDK-managed refresh to use the same local token
endpoint; changing the Calendar API URL does not change OAuth endpoints.

## JavaScript OAuth client

The sample uses the official modular `@googleapis/calendar` SDK and
`google-auth-library`:

```ts
import { calendar } from '@googleapis/calendar';
import { OAuth2Client } from 'google-auth-library';

const origin = 'http://127.0.0.1:4173';
const auth = new OAuth2Client({
  clientId: 'sample-app',
  clientSecret: 'local-sample-secret',
  redirectUri: 'http://127.0.0.1:4175/callback',
  endpoints: {
    oauth2AuthBaseUrl: `${origin}/oauth/authorize`,
    oauth2TokenUrl: `${origin}/oauth/token`,
    oauth2RevokeUrl: `${origin}/oauth/revoke`,
  },
});
const api = calendar({ version: 'v3', auth, rootUrl: origin });
// After the callback: auth.setCredentials((await auth.getToken(code)).tokens)
const profile = await auth.request({ url: `${origin}/userinfo` });
const calendars = await api.calendarList.list();
const { data } = await api.freebusy.query({
  requestBody: {
    timeMin: '2026-10-19T00:00:00+09:00',
    timeMax: '2026-10-20T00:00:00+09:00',
    items: [{ id: 'primary' }],
  },
});
console.log(data.calendars?.primary?.busy);
```

Register the exact callback URL in the fixture. The built-in client is
`sample-app` with secret `local-sample-secret`; these are deliberately public
local test values. Never use a real Google client secret here.

With the token response assigned using `auth.setCredentials`, this client's
refresh requests use the configured local token endpoint. See
[OAuth2Client endpoint options](https://github.com/googleapis/google-auth-library-nodejs/blob/main/src/auth/oauth2client.ts).

The sample verifies OAuth state using a short-lived HttpOnly cookie. It blocks
outbound SDK requests to non-loopback hosts and disables redirects, including
accidental requests to real Google endpoints. The automated SDK integration test
runs with separate ephemeral ports and repeats the workflow after reset.

## Sample configuration

| Environment variable   | Default                              |
| ---------------------- | ------------------------------------ |
| `CALENDARPIT_URL`      | `http://127.0.0.1:4173`              |
| `SAMPLE_PORT`          | `4175`                               |
| `SAMPLE_CLIENT_ID`     | `sample-app`                         |
| `SAMPLE_CLIENT_SECRET` | `local-sample-secret`                |
| `AUTHORIZATION_URL`    | Provider origin + `/oauth/authorize` |
| `TOKEN_URL`            | Provider origin + `/oauth/token`     |
| `USERINFO_URL`         | Provider origin + `/userinfo`        |
| `CALENDAR_API_URL`     | Provider origin                      |

These environment switches belong in the consuming application. Its maintainers
should verify all endpoint overrides, callback reachability and the complete UI/worker
flow. Calendarpit provides generic compatibility tests; consumer-specific fixtures and
E2E scenarios belong to the consumer repository. See [Incremental sync](/calendarpit/sync/) for
watch-driven event refresh.
