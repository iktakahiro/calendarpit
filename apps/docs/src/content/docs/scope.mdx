title: Scope and limitations
description: What Calendarpit covers, what it leaves out, and the current project status.
---

Calendarpit is a local Google Calendar-compatible API and OAuth server for developing and testing your app without a real Google account, Google Cloud project, or network access to Google. It implements the subset of the Google Calendar API v3, OAuth 2.0, incremental sync, and webhook notifications needed for local development, CI, and end-to-end tests.

## What is covered

- **Runtime and state**: One Bun process serves the API, OAuth flow, and admin UI on `http://127.0.0.1:4173` by default, using SQLite or `:memory:` storage ([Run and configure](/calendarpit/running/), [Storage and restarts](/calendarpit/storage/)).
- **Test users and calendars**: Passwordless test users own calendars, each with an IANA time zone; each user's primary calendar is reachable as `primary`, read via `calendarList.list` and `calendars.get`.
- **Events and availability**: Event CRUD (`list`, `get`, `insert`, `update`, `patch`, `delete`, `instances`), recurrence (a subset of `RRULE`/`EXRULE`/`RDATE`/`EXDATE`) with exceptions (listing or expanding a calendar that contains a series without `COUNT` or `UNTIL` requires `timeMax` whenever `timeMin` or `singleEvents=true` is used), DST-aware `[start, end)` intervals, ETags, extended properties, local invitations and RSVP, stored reminders, synthetic `hangoutsMeet` links, and `freebusy.query` ([Calendar API compatibility](/calendarpit/compatibility/), [Events, recurrence and time](/calendarpit/recurrence/)).
- **OAuth**: Local consent page with test-user selector, approval/denial, `state` preservation, exact `redirect_uri` checks, code exchange, `S256` PKCE, scope checks, refresh tokens, `/userinfo`, and revocation ([Local OAuth](/calendarpit/oauth/)).
- **Incremental sync**: `nextSyncToken` and `syncToken` on `events.list`, frozen paginated snapshots, `status: "cancelled"` tombstones, and `410 fullSyncRequired` responses ([Incremental sync](/calendarpit/sync/)).
- **Watch**: `events.watch` and `channels.stop`, `sync` and `exists` webhooks, callback host allowlist, up to 3 delivery attempts, channel expiry, and `POST /__calendarpit/deliveries/drain` ([Watch notifications](/calendarpit/watch/)).
- **Admin UI**: Day and week views, basic event editor, user and calendar management, connection revocation, watch and delivery logs, masked request history, and fixture/reset controls.
- **Test control**: Startup JSON fixtures with optional fixed IDs and `/__calendarpit/*` management endpoints to inspect state, load fixtures, reset to the baseline, and manage data ([Fixtures](/calendarpit/fixtures/), [Test control API](/calendarpit/test-control/)).

## Guarantees

- **Loopback by default**: The server binds to `127.0.0.1` unless you set `--host` or `CALENDARPIT_HOST` (the `Dockerfile` default command binds `0.0.0.0` inside the container). Webhook callbacks only target loopback hosts unless you configure `CALENDARPIT_WATCH_HOSTS`.
- **Explicit errors for unsupported features**: Unsupported Calendar API endpoints return `501`, and unsupported query parameters, fields, and recurrence rules return `400`, all with `reason: "unsupportedFeature"` (`events.import` returns `404 notFound`, and `events.quickAdd` returns `400 unsupportedFeature` for its `text` parameter or `404 notFound` without it). OAuth authorization requests with unsupported parameters return `400` with `error: "unsupported_feature"`. Unsupported OAuth endpoints return `501` with `error: "unsupportedFeature"`. Calendarpit rejects an unsupported recurrence rule with `400 unsupportedFeature` instead of storing the event without it.
- **No real Google calls**: Calendarpit never sends API, OAuth, or webhook requests to Google. (The admin UI loads the Roboto Mono font from Google Fonts with a system-font fallback.)
- **Deterministic reset**: `POST /__calendarpit/reset` clears tokens, channels, history, and edits, restoring the startup fixture with the same IDs. In SQLite mode, the reset baseline survives restarts; set fixed IDs in the fixture for IDs that stay stable across `:memory:` restarts.

## What is out of scope

- **ACLs, shared calendars, and delegation**: Users only access their own calendars (`accessRole: "owner"`). All `acl.*` methods return `501 unsupportedFeature`.
- **Other CalendarList and Settings methods**: `calendarList.list` is read-only (with `showDeleted=true` tombstones for calendars deleted via the management API or admin UI) and does not issue `nextSyncToken`. Other `calendarList.*` methods and all `settings.*` methods return `501 unsupportedFeature`.
- **Calendar writes, colors, and `events.import`/`quickAdd`/`move`**: `calendars.insert`, `update`, `patch`, `delete`, and `clear`, `colors.get`, and `events.import`, `quickAdd`, and `move` are not implemented (manage calendars via the admin UI or management API; see [Calendar API compatibility](/calendarpit/compatibility/)).
- **Real invitation and reminder email**: `sendUpdates` records notification intent in `/__calendarpit/state` instead of sending email. Reminders are stored, but nothing fires.
- **Real Google Meet**: Conference requests generate deterministic `https://meet.calendarpit.invalid/<id>` URLs without creating real meetings.
- **Full OIDC**: Passwords, real Google login, `id_token` issuance, and JWKS/discovery endpoints are not supported.
- **Other protocols and real Google sync**: Microsoft Graph, CalDAV, and syncing with real Google Calendar are excluded.
- **Dragging events in the admin UI**: Moving or resizing events by dragging is not implemented. The admin views show a recurring series (not its occurrences) only on its start date, plus any stored exceptions on their own dates. The admin editor only covers basic fields; saving an event in the admin editor replaces it with only the basic fields, which removes recurrence (cancelling stored exceptions), attendees (cancelling their invitation copies), reminders, conference data, color, and visibility. Set those fields via the API (fixtures store these fields as-is without creating invitation copies or synthetic meeting links; see [Fixtures](/calendarpit/fixtures/)).

## A workflow Calendarpit reproduces

Calendarpit reproduces this end-to-end integration workflow (for the Google SDK sample flow, see [SDK examples](/calendarpit/sdks/)):

1. Authorize as a test user on the local consent page and select a calendar.
2. Register an `events.watch` channel and receive the initial `sync` notification.
3. Create an event and verify its busy interval with `freebusy.query`.
4. Update and delete the event, receive `exists` notifications, and refetch state.
5. Stop the watch channel with `channels.stop` and confirm further changes are not delivered.
6. Revoke the connection and reconnect through OAuth.
7. Deny consent and verify that `state` is preserved without losing existing tokens.
8. Reset with `POST /__calendarpit/reset` and repeat the flow with the same fixtures and IDs.
9. Fetch a full `events.list` snapshot, then consume changes and `status: "cancelled"` deletions with `syncToken`.
10. Exercise all-day events (including `dateTime: null`), recurring exceptions, local RSVP, and synthetic meeting links.

## Current status

- **Runs from a clone**: No npm package, Docker Hub image, or GitHub release is published yet. Clone the repository and run it with Bun `1.4.3` ([Quick start](/calendarpit/quick-start/)).
- **Host-platform standalone executable**: `bun run build:binary` builds a standalone executable for the current host platform only.
- **Unvalidated Docker setup**: A `Dockerfile` exists in the repository, but container build and startup are not validated yet.
