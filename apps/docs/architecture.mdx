## Code organization

Calendarpit groups code by feature and gives every file one of a few explicit
roles. The scoped guides
[`packages/server/AGENTS.md`](https://github.com/iktakahiro/calendarpit/blob/main/packages/server/AGENTS.md)
and
[`apps/calendarpit/AGENTS.md`](https://github.com/iktakahiro/calendarpit/blob/main/apps/calendarpit/AGENTS.md)
list the directories and rules. `architecture.test.ts` in each workspace enforces
the import rules, and Oxlint rejects import cycles.

### Why not full DDD or onion layers

The domain model of an emulator is the Google API contract. Its resource shapes
are fixed by the upstream API, so entity classes and DTO mappers would describe
the same JSON twice. There is also a single storage mechanism: an in-memory
working set checkpointed to SQLite. Repository interfaces and a DI container
would add indirection without a second implementation to swap in.

Two ideas from those approaches still pay off, and the layout keeps them:

- **Invariants live in one place.** Validation and calculations are plain
  functions in rule modules, free of HTTP and storage, so they can be unit-tested
  directly.
- **Dependencies point inward.** HTTP route modules call operations, and
  operations call rules. Rules never depend on the workspace or on `Request`.

### Server layers

Shared helpers sit at the bottom: `shared/` holds domain-neutral errors and
validation, and `model/` holds type-only record shapes. Next come `workspace/`
(state and persistence) and `http/` (request and response handling). Feature
directories sit on top. Inside a feature, the suffix gives each file its role:

| Suffix           | Role                                                       | May import                 |
| ---------------- | ---------------------------------------------------------- | -------------------------- |
| `-routes.ts`     | HTTP adapter for Google-compatible or management endpoints | everything below, `http/`  |
| `-operations.ts` | Reads and changes workspace state as one unit of work      | rules, `workspace/`        |
| none             | Rule module: validation, invariants, and calculations      | `shared/`, `model/`, rules |

Features may use another feature's rules and operations, but never its routes.
Google-compatible routes and management routes share operations; they differ
only in authentication and response shape.

### Admin UI layers

Route files parse URL params and search and render one feature screen. Each
feature owns its `components/`, `hooks/`, and pure `models/`. Server state is
read and changed through TanStack Query hooks. Code moves to the shared
`components/` or `lib/` only when it has no feature knowledge.

### Documentation

Every exported function, class, type, and constant has TSDoc. The comment covers
the contract: purpose, errors thrown, and the Google behavior it mirrors or
rejects. Readers of the published package and contributors use the same
comments.

## Runtime and state

`createCalendarpit()` owns a workspace per instance and exposes an async Web Request
handler. It returns null for UI routes. TanStack Start delegates protocol requests
to that handler before rendering pages. The CLI and dev server default to a local
SQLite file through Bun's built-in `bun:sqlite`; the programmatic factory defaults
to `:memory:` for isolated embedded tests. No external database server is needed.

The workspace keeps its working set in memory and checkpoints a versioned JSON snapshot
into one SQLite row. A single atomic statement saves the fixture baseline, current
data, grants/tokens, sync snapshots, calendar tombstones, subscriptions, and bounded logs together. Unchanged snapshots
are not rewritten. File databases use WAL and FULL synchronization. A separate
SQLite lock file holds an exclusive lock for the lifetime of the instance, preventing
two independent instances from overwriting the same workspace. OS locks release on exit,
including crashes; no stale PID cleanup is needed. Database and lock files use mode 0600.

A new database validates and captures its seed fixture. Existing databases restore
saved data and the original reset target, preserving event IDs, timestamps, and etags.
Loading another fixture replaces current data without replacing that target.
Schema version 1 is supported; newer versions are rejected without overwriting data.
Optional sync snapshots, calendar tombstones and notification-intent fields default
to empty collections when opening older version-1 snapshots. Future incompatible
format changes require an explicit migration.

Event time conversion uses Temporal with explicit time zones. API authorization,
resource ownership, interval calculations, and lifecycle rules live in the server
package, independent of React and the consuming application. The injected clock
and delivery function support expiry and cancellation tests without sleeps.

Watch callbacks use per-channel promise queues, abort signals, bounded retries,
and observable delivery records. Reset invalidates tokens, consent, cursors,
history, channels, and queued/in-flight deliveries before restoring fixture data.
Restart preserves access/refresh tokens and unexpired channels, rechecking callback
host permissions. Event sync tokens also survive restart. Consent, authorization codes, and pagination cursors are ephemeral.
Pending notifications become cancelled records on restart and are not replayed.
HTTP bodies are limited to 1 MiB; protocol history and delivery logs are bounded.

## UI

React 19 and TanStack Start provide file-based routing and SSR. Kumo supplies UI
components; Tailwind CSS 4 scans Kumo's distribution for classes after loading
its theme. The app root is isolated for portal stacking. Application icons use
Gravity UI; Phosphor Icons is also a required Kumo peer for internal icons.
The admin UI uses Roboto Mono from Google Fonts with system-font fallbacks.

The event editor uses TanStack Form. Management state polls every two seconds
so mutations from another application appear without reloading the page. Calendar
operations use explicit management routes, not TanStack server functions.

## Packaging

Bun provides installs, scripts, tests, type checking, HTTP serving, and compilation.
Vite transforms the client/server while running on Bun. The production CLI serves
an allowlisted map of built assets and delegates other requests to the server.
Paths never resolve to arbitrary disk files. The standalone binary embeds server,
assets and runtime. The admin UI loads Roboto Mono from Google Fonts,
with system-font fallbacks when unavailable. Calendar and OAuth operations remain
local. Fixture configuration is loaded before server startup.

Docker configuration remains available but its build/startup verification is
pending. The docs preview and sample are separate development processes. Dependency
resolution observes the repository's 48-hour publication interval.
