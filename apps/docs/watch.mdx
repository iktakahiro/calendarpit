## Register and stop

Use `POST /calendar/v3/calendars/{calendarId}/events/watch` with a unique `id`,
`type: web_hook`, callback `address`, optional `token`, and optional Unix-millisecond
`expiration`. The response contains `kind: api#channel`, `id`, `resourceId`,
`resourceUri`, expiration, and the optional token. IDs are limited to 64 ASCII
letters/digits/underscores/hyphens. Tokens are limited to 256 characters.

Send `id` and `resourceId` to `POST /calendar/v3/channels/stop` using a token from
the connection that created it. Stop returns 204. Channels default to 24 hours
and are capped at seven days; register a new channel to renew.

## Deliveries

Each channel receives an initial `sync` notification (message number 1), followed
by `exists` after successful event mutations. Notifications are empty POSTs with
`X-Goog-Channel-ID`, `X-Goog-Resource-ID`, `X-Goog-Resource-URI`,
`X-Goog-Resource-State`, `X-Goog-Message-Number`, and
`X-Goog-Channel-Expiration`. The optional channel token is echoed in
`X-Goog-Channel-Token`. Numbers increase per channel; retries reuse the same number.
The receiver must refetch events. No event payload is sent.

These wire conventions follow the
[Google Calendar push guide](https://developers.google.com/workspace/calendar/api/guides/push).
Calendarpit intentionally permits local HTTP callbacks, unlike Google's HTTPS
requirement. Callback timing may precede the watch response.

## Local delivery policy

Callbacks allow literal `127.0.0.1`, `[::1]`, and `localhost` by default.
`localhost` is pinned to `127.0.0.1` for delivery. To reach Docker/service-network
hosts, explicitly set a comma-separated `CALENDARPIT_WATCH_HOSTS` allowlist on
the server. Additional hosts may resolve through DNS and should be trusted test
services. Credentials in URLs, fragments, and redirects are rejected. OAuth
access tokens are never attached to callbacks.

Delivery is serialized per channel and independent of event persistence. There
are up to three attempts, each with a two-second timeout and a 100 ms retry delay.
HTTP 200, 201, 202, and 204 indicate success. There is no durable queue or guarantee
of delivery across process restarts. SQLite restores unexpired subscriptions and
message counters, while interrupted deliveries are marked cancelled without replay.
Refetch state after a server restart. Memory mode discards all subscriptions. The admin screen shows the latest 200
delivery records and their attempt counts/status.

Stop, expiration, connection revocation, calendar removal, and reset prevent
future deliveries. Stop/revocation/reset abort in-flight requests and queued work;
an already-received request cannot be withdrawn from a remote application.
Expiry is checked before attempts and when channels are inspected or events change.
Use `POST /__calendarpit/deliveries/drain` to await currently queued work in tests.

## Incremental refresh

After receiving a notification, call `events.list` with the last `nextSyncToken`.
Process every page, upsert returned events, remove cancelled entries, and only then
save the final page's next token. HTTP 410 requires a new full synchronization.
See [Incremental sync](/sync) for a complete loop. The initial watch notification
is a signal to fetch state, not an event snapshot.
